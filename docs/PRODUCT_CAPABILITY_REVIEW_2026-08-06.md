# 工作记忆 Agent 当前能力、置信度与产品路线总结

> 评估日期：2026-08-06
> 评估范围：Rust canonical runtime/server、工作记忆 Bucket 流程、Agent Harness 基础设施，以及后续问答和 Codex 集成方向。
> 本文是产品层面的现状总结和规划，不包含代码修改方案。

## 1. 一句话结论

当前项目已经具备一个可以实际运行的**工作记忆归档 MVP**，能够调用真实模型完成分类、提取、Bucket 创建、Bucket 追加、询问确认和持久化。

但当前产品的核心入口仍然偏向“归档请求”，还没有完全形成下面这条面向用户的闭环：

```text
用户输入
  → 意图判断
  → 记忆检索 / 归档 / 工具调用
  → 生成带证据的回答
  → 用户确认后执行写操作
```

因此当前更准确的产品定位是：

> **带有 Agent 工具基础设施的工作记忆归档 MVP，而不是完整的个人工作 Agent。**

---

## 2. 当前已经具备的能力

### 2.1 真实模型调用

Rust 服务已经可以从 `.env` 或进程环境变量读取模型配置，并调用真实模型完成结构化输出。

当前模型调用主要用于：

- 判断输入应该追加到已有 Bucket、创建新 Bucket，还是请求确认；
- 选择候选 Bucket；
- 返回分类理由和置信度；
- 提取摘要、TODO、证据、时间线、决策、假设、实体和标签等结构化信息；
- 将分类审计和提取结果持久化到 SQLite。

因此，模型 API 调用本身已经可以工作，不再只是 mock 测试或静态规则。

### 2.2 Bucket 生命周期

当前已经支持以下核心操作：

| 能力 | 当前状态 | 说明 |
| --- | --- | --- |
| 追加已有 Bucket | 已实现 | 明确匹配时保存到已有 Bucket |
| 创建新 Bucket | 已实现 | 生成 Bucket 标题和类型，并保存第一条 Entry |
| 请求用户确认 | 已实现 | 不安全时返回 `ask_user`，不正式创建 Entry |
| 确认后追加 | 已实现 | 通过显式确认接口追加到指定 Bucket |
| 确认后创建 | 已实现 | 通过显式确认接口创建并保存新 Bucket |
| Bucket 搜索 | 已实现 | 支持按关键词搜索 Bucket/记忆内容 |
| Bucket 详情 | 已实现 | 查看 Entry、摘要、TODO、证据、时间线和决策 |
| Bucket 状态管理 | 已实现 | 支持 active、paused、archived 等状态 |
| Entry 纠错移动 | 已实现 | 移动到正确 Bucket，并保留纠错审计 |

当前 Rust Server 的主要公开路由包括：

```text
GET  /health
GET  /api/buckets/active
GET  /api/buckets/search
GET  /api/buckets/:id
POST /api/archive
POST /api/archive/append
POST /api/archive/create
POST /api/corrections/move
POST /api/buckets/status
```

### 2.3 结构化记忆

系统不是简单地把原文塞进数据库，而是尝试从每条 Entry 中提取：

- `summary`：摘要；
- `todo`：待办；
- `evidence`：日志、指标、错误信息等证据；
- `timeline`：带时间的事件；
- `decision`：决策及原因；
- `hypothesis`：假设；
- `entity`：项目、服务、接口等实体；
- `tag`：便于检索和概览的标签。

原始输入仍应被视为事实来源，结构化结果是派生信息，不能完全替代原文。

## 3. 真实分类效果与置信度判断

### 3.1 手工真实模型测试结果

一次真实模型手工测试执行了 23 条归档请求，包含明确追加、明确创建和低信息模糊输入。

| 场景 | 数量 | 结果 |
| --- | ---: | --- |
| 明确追加已有 Bucket | 6 | 6/6 正确 |
| 明确创建新 Bucket | 3 | 3/3 正确 |
| 模糊输入，应该询问 | 14 | 8/14 正确拦截 |
| 总体动作判断 | 23 | 17/23，约 73.9% |

明确输入的分类效果较好，例如：

```text
支付回调现在错误率降到 0.2% 了
→ 支付回调失败排查
confidence: 0.99
```

```text
连接池调到 100 后 P99 降到 1.4 秒
→ 接口 A 压测
confidence: 0.93
```

```text
Agent 的数据库模型已经完成
→ 个人事务 Agent MVP
confidence: 0.99
```

明确创建新 Bucket 的输入也可以正确识别，例如：

```text
不要放到接口 A，另开接口 B 压测
→ create_new / experiment
```

```text
线上登录接口突然大量返回 401，单独记一个故障
→ create_new / incident
```

```text
单独整理一份 SQLAlchemy 事务笔记
→ create_new / knowledge
```

### 3.2 当前置信度的本质

当前 `confidence` 应理解为：

> 模型对当前分类选择的主观评分，而不是经过统计校准的真实正确概率。

例如：

```text
confidence: 0.99
```

不应直接解释为：

```text
这条判断有 99% 的概率正确。
```

它更接近于：

```text
在当前候选和提示词下，模型非常倾向于这个 Bucket。
```

### 3.3 主要风险：模糊输入过度自信

以下类型的输入信息量很低，但模型可能给出很高的置信度：

```text
压测结果更新了
上次评审的事项完成了
Agent 那个任务继续
把校验相关的记一下
切备用后好了
它现在正常了
```

这类输入的问题不是“找不到相似 Bucket”，而是：

- 模型可以找到一个看起来最像的 Bucket；
- 但用户没有提供足够的新事实；
- 代词、时间指代和上下文可能没有被正确解析；
- 如果直接写入，可能污染长期记忆；
- 之后问答会把猜测当成事实使用。

所以：

> **分类匹配度高，不代表信息足够安全地写入。**

### 3.4 现有门控策略

当前门控大致采用：

- `confidence >= 0.85`：允许自动归档；
- `0.55 <= confidence < 0.85`：请求确认；
- 多候选或候选不安全：请求确认；
- 低于 `0.55`：请求确认；
- `ask_user`：只保存归档尝试和审计，不正式写入 Entry。

这套机制已经能拦截一部分风险，但不能只依赖模型给出的单一分数。

### 3.5 评测数据的口径

仓库中还有一份 2026-08-03 的 50 条真实模型评测报告。该报告是在增加低信息指代门控之后得到的结果：

- action 准确率：96%；
- 自动归档准确率：100%；
- `ask_user` 覆盖率：100%；
- 严重误合并：0。

这份报告与上面的 23 条手工场景测试使用的案例集和测试阶段不同，不能直接当作同一组统计结果。两者共同说明：

1. 明确输入的分类能力已经较好；
2. 服务端风险门控比单纯调整阈值更重要；
3. 低信息输入仍然需要持续回归测试；
4. 当前置信度还没有达到生产级概率校准的程度。

## 4. “创建、分类、询问、回答”四项能力判断

### 4.1 Bucket 创建：可以

当前能够：

1. 判断输入不适合已有 Bucket；
2. 生成新 Bucket 标题；
3. 选择 Bucket 类型；
4. 创建 Bucket；
5. 保存第一条 Entry；
6. 生成结构化记忆。

后续仍需要防止：

- 新 Bucket 与已有 Bucket 重复；
- 模糊输入导致错误创建；
- Bucket 数量无限增长；
- 同义主题被拆成多个 Bucket。

建议未来增加 Bucket 相似度检查、合并、重命名、别名和生命周期管理。

### 4.2 Bucket 分类：明确输入基本可靠

包含项目名称、接口名称、故障现象、指标和具体动作的输入，通常可以稳定分类。

风险主要来自：

- “那个任务”；
- “上次评审”；
- “它好了”；
- “继续”；
- “更新了”；
- “校验相关”；
- 多个 Bucket 都包含相同领域词。

分类系统应该把“目标 Bucket 是否匹配”和“输入是否足够写入”分成两个判断。

### 4.3 用户询问确认：机制已经有，但召回还需要加强

后端已经支持 `ask_user`，并且有显式确认追加和确认创建接口。

比较理想的交互应该让用户可以选择：

```text
我认为这条内容可能属于「接口 A 压测」，但信息不够明确。

1. 保存到「接口 A 压测」
2. 选择其他 Bucket
3. 创建新 Bucket
4. 不保存
```

当前需要继续优化的是：

- 模糊输入更早触发询问；
- 展示模型的推荐和理由；
- 支持用户直接改选目标 Bucket；
- 支持“这条不保存”；
- 将用户的确认和纠正反馈纳入评测。

### 4.4 通过 API 回答问题：Rust 公共入口尚未完整闭环

当前模型 API 已经用于分类和提取，但 Rust `work-memory-server` 的公开路由主要仍是归档和 Bucket 查询路由，当前没有统一的：

```text
POST /api/chat
POST /api/ask
POST /api/agent
```

因此现在可以做到：

1. 通过搜索 API 查询 Bucket 或 Entry；
2. 将查询结果交给其他客户端；
3. 由客户端再调用模型进行总结。

但还没有在 Rust Server 中完整实现：

```text
用户问题
  → 自动检索相关记忆
  → 组织证据
  → 调用模型生成自然语言答案
  → 返回来源、时间和不确定性
```

仓库中已经存在 Agent Harness、聊天消息持久化和受限工具循环的底层基础设施；Python legacy Harness 也保留了面向对话和记忆工具的实现。但是这些能力需要进一步统一到 Rust Server 的产品入口，才能形成稳定的“问答—检索—工具—归档”闭环。

## 5. 推荐的统一产品入口

建议未来增加一个统一的会话入口，例如概念上的：

```text
POST /api/chat
```

或：

```text
POST /api/turn
```

内部先判断意图：

```text
用户输入
  ↓
意图路由
  ├── archive：新事实，需要保存
  ├── ask：询问历史记忆
  ├── action：希望系统执行任务
  ├── mixed：既要回答，又要保存或执行
  ├── chat：普通对话
  └── clarify：无法安全判断，需要询问
```

### 示例：纯归档

```text
今天支付回调错误率下降到 0.2%。
```

流程：

```text
分类 → 提取 → 归档
```

### 示例：纯问答

```text
上次支付回调失败的原因是什么？
```

流程：

```text
识别问题
→ 搜索相关 Bucket 和 Entry
→ 汇总证据
→ 生成答案
```

### 示例：混合请求

```text
刚刚修复了连接池问题，告诉我之前为什么出错，并把修复结果记下来。
```

流程：

```text
查询历史原因
→ 生成回答
→ 提议将修复结果写入相关 Bucket
→ 用户确认后保存
```

### 示例：执行任务

```text
帮我检查这个 Rust 项目为什么测试失败。
```

流程：

```text
检索项目历史
→ 调用代码工具或 Codex
→ 运行检查
→ 总结结果
→ 询问是否归档结论
```

## 6. 置信度系统的下一步优化

### 6.1 将单一 confidence 拆成多个维度

建议逐步增加以下判断字段：

```text
match_confidence          # 与目标 Bucket 的匹配程度
information_sufficiency   # 信息是否足够
ambiguity_score           # 歧义程度
reference_resolution     # “它”“那个”“上次”是否解析清楚
write_risk                # 写错的影响
requires_confirmation     # 是否必须确认
```

自动归档应该要求同时满足：

```text
目标唯一
且信息充分
且代词已经解析
且不是模糊续写
且写入风险低
且服务端规则通过
```

例如：

```text
匹配度 0.98，但信息充分度只有 0.40
```

最终仍然应该：

```text
ask_user
```

### 6.2 增加确定性风险规则

以下情况建议默认请求确认：

- 输入过短；
- 只有“完成了”“更新了”“继续”“好了”等状态词；
- 含有“它”“那个”“上次”等代词，但缺少可解析上下文；
- 多个候选 Bucket 分数接近；
- 模型想创建新 Bucket，但没有清晰主题；
- 新 Bucket 与已有 Bucket 高度相似；
- 内容没有明确事实、指标、决策、证据或行动变化；
- 用户没有表达明确的保存意图，且输入更像普通问题或闲聊。

### 6.3 建立可重复的评测体系

建议维护至少三组测试集：

1. 明确追加集；
2. 明确创建集；
3. 模糊和高风险输入集。

重点指标：

```text
action accuracy
existing Bucket accuracy
new Bucket precision
auto-archive precision
ask_user recall
serious merge count
false new Bucket count
```

工作记忆系统中，自动写入的精确率通常比盲目追求召回率更重要。错误归档会污染后续检索和回答，因此宁愿多询问一次，也不要静默写错。

### 6.4 做置信度校准，而不是只调阈值

后续可以使用人工标注样本计算：

- 置信度分桶后的实际正确率；
- Brier score；
- Expected Calibration Error；
- 不同阈值下的自动归档精确率和询问召回率。

模型分数、服务端规则和历史纠正结果应该共同决定最终动作。

## 7. 问答能力的产品设计

### 7.1 检索流程

回答问题时建议采用：

```text
问题
  → 提取实体、主题、时间和状态
  → 搜索 Bucket、Entry、summary、tag、entity
  → 按相关性和时间重排
  → 选择有限证据
  → 调用模型生成回答
  → 返回来源和不确定性
```

后续可以从关键词搜索逐步升级到混合检索：

- Bucket 名称搜索；
- Entry 原文搜索；
- summary、tag、entity 搜索；
- 时间范围过滤；
- 状态过滤；
- 关键词检索；
- 语义检索；
- 结果重排；
- 多 Bucket 合并回答。

### 7.2 回答必须带证据

推荐的回答结构：

```text
结论：
支付回调问题主要与第三方网关升级有关。

来源：
- Bucket：支付回调失败排查
- Entry：某日的故障记录
- Entry：某日的恢复记录

不确定性：
目前没有找到正式关闭故障的记录。
```

系统应明确区分：

- 数据库中明确存在的事实；
- 根据多条记录做出的推断；
- 数据库中没有找到的内容。

如果没有证据，应明确回答“当前记忆中没有找到”，而不是让模型自由补全。

### 7.3 需要支持的时间和状态问题

未来应能回答：

```text
最近一周有哪些未完成事项？
哪些问题已经解决？
上个月接口稳定性有哪些变化？
哪些决定还没有落地？
```

这要求记忆系统不仅保存文本，还要理解：

- 时间；
- 状态；
- 负责人；
- 截止日期；
- 任务和决定；
- 当前有效性；
- 新旧事实之间的关系。

## 8. Agent 工具层规划

建议将工具按风险分级。

### 低风险：可以自动执行

```text
search_memory
list_active_buckets
get_bucket_detail
read_entry
run_tests
inspect_repository
```

### 中风险：执行前建议确认

```text
archive_memory
save_to_existing_bucket
create_bucket
move_entry
change_bucket_status
```

### 高风险：必须明确确认

```text
apply_patch
git_commit
git_push
deploy
delete_file
run_production_command
send_message
access_secrets
```

所有工具调用都应有：

- 白名单；
- 参数 Schema 校验；
- 最大调用轮数；
- 超时；
- 输出大小限制；
- 审计日志；
- 幂等键；
- 失败恢复策略；
- 写操作确认；
- 权限和网络边界。

## 9. Codex 集成方向

Codex 适合作为 Agent 的**代码执行型工具**，而不是替代工作记忆系统。

推荐的产品关系：

```text
工作记忆 Agent
    ↓
run_coding_task 工具
    ↓
Codex 或隔离的代码执行 Worker
    ↓
测试结果、修改内容、差异、日志
    ↓
Agent 总结
    ↓
用户确认是否归档
```

### 9.1 一个完整的使用场景

用户：

```text
帮我检查这个 Rust 项目的测试失败原因，修复后告诉我结果。
```

系统：

1. 从工作记忆中找到相关项目和历史问题；
2. 确定当前仓库和任务范围；
3. 调用 Codex 或代码执行 Worker；
4. 读取代码并运行测试；
5. 分析失败原因；
6. 生成补丁；
7. 再次运行测试；
8. 返回修改内容、测试结果和未解决问题；
9. 询问是否将结论保存到相关 Bucket。

### 9.2 建议的工具抽象

```text
run_coding_task(
  repository,
  task,
  mode,
  allowed_commands,
  timeout
)
```

`mode` 可以包括：

```text
read_only
run_tests
propose_patch
apply_patch
```

工具结果建议包含：

```text
task_id
status
summary
changed_files
diff
test_commands
test_results
error_logs
artifacts
```

### 9.3 安全边界

不要让模型拥有无限制的 Shell、文件系统、网络或生产环境权限。

建议默认策略：

| 操作 | 默认策略 |
| --- | --- |
| 查看代码 | 自动 |
| 搜索历史记忆 | 自动 |
| 运行单元测试 | 自动 |
| 运行格式化和静态检查 | 自动 |
| 生成补丁 | 可以自动生成，但不直接合并 |
| 应用补丁 | 用户确认 |
| `git commit` | 用户确认 |
| `git push` | 用户确认 |
| 部署 | 强制确认 |
| 删除文件 | 强制确认 |
| 读取密钥 | 禁止或单独授权 |

Codex 任务的结果不应该全部原样存入记忆。建议只归档：

- 任务目标；
- 问题原因；
- 采取的修改；
- 测试结果；
- 未解决问题；
- 相关文件；
- 补丁或提交信息。

大量终端日志应作为任务产物或附件保存，而不是直接污染 Bucket 正文。

---

## 10. 可继续增加的功能

### 10.1 反馈学习

用户可以说：

```text
这条应该放到接口稳定性治理。
```

系统应自动：

- 移动 Entry；
- 记录纠正；
- 更新分类评测数据；
- 降低类似误判再次发生的概率。

也可以支持：

```text
不要再把这类内容放进这个 Bucket。
```

### 10.2 Bucket 合并、拆分和别名

防止产生以下重复主题：

```text
接口 A 压测
接口A性能测试
接口 A 负载测试
```

建议支持：

- 合并 Bucket；
- 拆分 Bucket；
- 重命名；
- 别名；
- 父子 Bucket；
- 主 Bucket；
- 生命周期状态。

### 10.3 Todo 和提醒

从记忆中提取：

```text
下周检查压测报告
等产品确认首页方案
记得补充事务测试
```

并形成：

- 待办列表；
- 截止时间；
- 提醒；
- 任务状态；
- 关联 Bucket。

### 10.4 日报和周报

系统可以定期生成：

```text
本周完成了什么？
哪些问题仍然阻塞？
哪些 Bucket 变化最大？
有哪些待确认的决策？
```

### 10.5 多来源接入

可以逐步考虑接入：

- Git commit；
- GitHub Issue；
- Slack；
- 邮件；
- 会议纪要；
- IDE；
- 浏览器剪藏；
- 本地 Markdown；
- 终端命令和测试结果。

每种来源都应明确来源、时间、权限、自动归档策略和敏感数据边界。

### 10.6 冲突和版本管理

例如：

```text
数据库使用 SQLite。
```

后来又出现：

```text
数据库已经迁移到 PostgreSQL。
```

系统需要判断这是：

- 新版本覆盖旧版本；
- 不同环境的事实；
- 相互矛盾；
- 需要用户确认。

否则问答时可能把旧事实和新事实混在一起。

### 10.7 记忆质量评分

可以为每个 Bucket 维护：

```text
活跃度
最近更新时间
Entry 数量
信息密度
冲突数量
用户纠正次数
分类稳定性
```

这些信息可以帮助系统决定哪些 Bucket 应该优先检索、合并、归档或提醒用户整理。

## 11. 推荐产品路线

### Phase 1：可靠归档

目标：

- 明确输入自动归档；
- 模糊输入尽量询问；
- 降低错误 Bucket 污染；
- 纠错反馈可被记录；
- 新 Bucket 不重复泛滥。

建议目标：

```text
明确输入自动归档准确率 > 95%
模糊输入拦截率 > 90%
严重误合并数量 = 0
错误新建 Bucket 尽可能接近 0
```

### Phase 2：记忆问答

增加统一 Chat/Ask 入口，实现：

```text
问题识别
→ 记忆检索
→ 证据整理
→ 模型回答
→ 返回来源和不确定性
```

这是从“归档程序”升级为“工作记忆 Agent”的关键阶段。

### Phase 3：受控工具调用

让 Agent 能够调用：

```text
search_memory
read_bucket
archive_memory
move_entry
run_tests
inspect_repository
```

同时明确区分查询工具、写入工具、代码执行工具和外部系统工具。

### Phase 4：Codex 集成

先从低风险任务开始：

```text
读取代码
解释代码
运行测试
分析错误
生成修改建议
```

之后再逐步支持：

```text
生成补丁
应用补丁
创建分支
创建 Pull Request
```

不要一开始就允许 Agent 自动提交、推送或部署。

### Phase 5：主动工作助手

进一步增加：

- 日报和周报；
- 待办提醒；
- 项目风险提示；
- 决策追踪；
- 记忆冲突提醒；
- 多来源自动归档；
- 项目和任务的长期状态管理。

## 12. 最终能力判断

| 能力 | 当前判断 |
| --- | --- |
| Rust 服务运行 | 已经可以 |
| 真实模型调用 | 已经可以 |
| 明确内容分类 | 基本可靠 |
| 追加已有 Bucket | 可以 |
| 创建新 Bucket | 可以 |
| 结构化记忆提取 | 已有 |
| 模糊输入询问 | 机制已有，但仍需加强拦截 |
| Bucket 搜索和详情 | 可以 |
| Entry 纠错移动 | 已有 |
| 通过 Rust HTTP API 直接回答问题 | 尚未形成统一入口 |
| Agent Harness 底层能力 | 已有，仍需与产品入口进一步统一 |
| 多轮记忆问答闭环 | 需要继续完善 |
| Codex 执行代码任务 | 尚未接入产品闭环 |

最重要的下一步不是继续增加更多 Bucket 类型，而是完成：

```text
Chat / Ask
  → 意图判断
  → 记忆检索
  → 归档或工具调用
  → 带证据回答
  → 用户确认后写入
```

并优先解决：

```text
模糊输入过度自信
```

否则问答功能完成之后，仍可能因为错误归档的内容而生成错误答案。
