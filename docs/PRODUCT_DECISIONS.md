## 2. Entry 的删除、更正与彻底清除

Entry 是保存的用户原始记录，Memory 是派生内容；conversation message 和 archive audit 是独立记录。三者不能因为显示相同文本就被视为同一对象。

已确定的普通删除语义：撤销这一条 Entry，并停止让仅由它支持的 Memory 参与有效查询、证据、摘要、TODO 和后续模型上下文。不得把失去来源的 Memory 随意挂到其他 Entry 上。

- 写错内容：可先通过撤销旧记录、保存新记录完成；原文编辑与版本替代机制暂不承诺。
- 不再保留这一条有效记录：采用上述撤销语义；保留其他 Entry 与其他有效记忆。
- 彻底忘记某段内容：另设数据清除合同，需覆盖聊天、审计、派生内容及保留范围，不能把普通删除称为彻底清除。
- 审计证明发生过撤销，不应让已撤销事实重新进入有效回答。
- “原文保留”约束自动提取和整理不得擅自覆盖原文；用户显式撤销是独立操作。

当前实现仍是物理删除 Entry、Memory 外键置空并保留审计，没有实现上述完整撤销链路，也没有独立 HTTP Entry 删除入口。本轮文档更新不改数据库、路由或删除行为。

下一阶段须确定物理删除还是逻辑撤销的存储方式，并在单事务中处理依赖与审计，覆盖失败回滚、重复撤销、后续读取/历史卡片及数据库重开。多来源 Memory 只有在显式维护支持关系后才能按“仍有有效来源”保留；当前单个 `entry_id` 不能证明多来源支持。既有 `entry_id = NULL` 数据如何处理须单列，不能无依据认定来源或批量清除。

## 3. 近期前端 MVP 的验收范围

先验收完整行为，再定大规模视觉方案。完成本阶段不代表视觉风格定稿，也不限制以后调整布局或前端技术。

| 链路 | 最低验收要求 |
|---|---|
| 输入 → 分类 → 保存/询问 | 有原文、归属与原因；低信息不静默保存；状态清晰 |
| 四种归档确认 | 推荐、其他、新建、不保存均可操作；绑定原文且不可重放 |
| 查询 → 详情 → 证据 | 找得到记录；显示来源；撤销后不继续返回失效证据 |
| 移动与撤销 | 结果同步到 Bucket、Memory 和审计；失败不显示成功 |
| 任务 → 进度 → 取消 | 提案与批准分开；刷新/断线不重复提交；取消反馈真实 |
| 重启恢复 | 历史和 pending 可恢复；running 中断不自动重放 |

联合验收检查真实页面的空状态、加载、错误、重复点击、滚动和窄屏可操作性。先修阻碍使用的问题；全面配色、版式、动效和品牌风格另列后续阶段。保持 API 调用、业务状态和渲染职责清楚，避免把当前视觉细节写进后端合同。

## 4. API 与后端设计方向

OpenAPI 指 HTTP 接口规范。它用于描述既有和经批准的新能力，不作为绕过审批、扩展 MCP 写工具或暴露远程控制的理由。

后续交付应包含：

- 请求/响应/错误 schema 的统一来源，减少 DTO、校验和文档漂移；外部输入继续从 unknown 校验。
- 稳定 operationId、参数、状态码、可空字段、时间格式、现有列表限制及兼容策略；需要分页的地方单独定义，不虚构当前分页能力。
- 归档审批、撤销、任务取消、重复调用和结果未知时的合同；不对所有现有 POST 宣称幂等。
- SSE 事件 schema、顺序/版本、断线恢复与前端处理约定；MCP 保持独立协议与工具 allow-list。
- 契约生成、路由覆盖、代表性真实响应与不兼容变化检查；生成工具和 OpenAPI 版本在实施时评估。

近期沿用领域、应用、存储、HTTP/MCP 和运行时组装的分层。框架评估应比较继续 Hono 与采用其他框架的实际收益、迁移量、依赖、测试和 Node 原生 TS 兼容性；NestJS 只作为讨论过的候选，未决定采用。

远程接入不自动要求微服务、多实例或数据库更换。只有出现明确的部署、隔离或吞吐需求，才评估进程拆分、服务端数据库和分布式队列；不能把现有进程 PID 所有权机制直接当作分布式协调。当前不预建租户表、通用事件总线或空实现层。

## 5. 远期多人协作想法

保留的产品假设是：统一对话入口，通过 Bucket 沉淀可追溯的共享工作记忆。它尚未通过真实协作验证。

已识别的反例包括：多话题交错的指代歧义、一条输入涉及多个 Bucket、个人说法被误作团队决定、分歧被摘要掩盖、私人信息进入共享派生内容、全局“最近一条”误操作他人记录，以及保存记忆不等于通知或完成交接。

未来若重新启动该方向，需先定义身份、回复关系、空间与可见范围、事实来源、争议/共识、修改与审批权限，再用小团队实验验证。当前不为此修改 schema、开发成员管理或批准多用户公网部署。
