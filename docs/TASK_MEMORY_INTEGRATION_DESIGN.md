# Doggie 任务策略与腾讯记忆接入设计

日期：2026-11-15 更新。状态：**本地基础已实施；D3 的 L0 合成词法 smoke 阶段性完成，完整实验未完成**。本文仍只定义策略、边界和后续实验，不代表已接入 Doggie 生产路径、启用自动分发或完成真实数据同步。L0 结果见 [实验报告](D3_L0_SMOKE_REPORT.json)，范围与未通过项见 [D3 执行计划](D3_EXPERIMENT_PLAN.md)。

阅读顺序：先看 §1–§3 的产品行为，再看 §4–§6 的接入与故障边界，最后看 §7–§10 的实施、验收和待确认项。所有“拟议”“建议”均不代表能力已经存在。

## 1. 目标、范围与现有基线

### 1.1 本阶段目标

用户持续通过同一个 Doggie 入口提出目标、补充要求、查看结果。Doggie 在后台明确关联任务、选择执行者、构建必要上下文，通过长期记忆保持连续性。内部可以存在多个执行会话，用户不必手工维护 session ID。

腾讯 TencentDB-Agent-Memory 是拟采用的记忆能力提供方；Doggie 继续负责个人助手的产品规则、来源有效性与受批准执行。验证通过后允许替换现有重叠能力，不以保留既有代码量为目标。

本阶段先验证“一个任务交给一个执行者”，不预建自动任务树、多个 Agent 并行、团队成员权限、远程接入、定时执行或插件生态。多人协作仍为远期假设；个人多设备继续仅保留 [远程接口设计](REMOTE_ACCESS.md)。

### 1.2 当前已有与尚缺能力

基线参考提交 `0a8ad83`；源码以实际工作分支为准。

| 对象/能力 | 当前事实 | 本设计的变化 |
|---|---|---|
| 聊天入口 | 持久化聊天与有界模型上下文；已支持 WorkItem 目标消息关联 | 保留入口，后续再评估自然语言自动归属 |
| Bucket / Entry | 主题组织、归档门控、原文与撤销 | 保留业务权威，不映射成腾讯 Team |
| TODO | schema v7 的 `memory_items`、五状态、计划/截止、重复推进 | 保持其身份与状态，不因记忆回写自动改变 |
| 后台队列任务 | `TaskSnapshot` 表达一次后台工作的运行状态 | 继续作为运行机制，不当作长期用户目标 |
| CLI AgentTask | 绑定指令、批准、session、backend、workspace 与结果 | 作为一次具体执行，不直接改名为用户目标任务 |
| CLI AgentSession | 绑定 backend/workspace/记忆版本，支持受限恢复 | 在既有约束上增加任务归属判断 |
| 分发策略 | 已支持明确 WorkItem 的手工创建提案与批准；不做自动任务归属 | 后续以实验结果决定是否增加自动归属 |
| 前端 | 2026-11-12 已完成工作区与视觉初版 | 增量补交互，不以重做视觉为接入前提 |
| 腾讯记忆 | 尚未接入 | 先独立验证，再决定采用层级与替换范围 |

参考：[Agent 控制](AGENT_CONTROL.md)、[撤销合同](ENTRY_REVOCATION.md)、[前端基线](FRONTEND_DESIGN.md)、[T14](T14_PLAN.md)、[现有架构](ARCHITECTURE_DECISIONS.md)。本设计不改写这些文档中已交付能力的历史验收结果。

## 2. D1：Doggie 的最小行为策略

### 2.1 概念与关联

本文将用户目标任务称为 **WorkItem**，避免与 TODO、后台 `tasks` 和 CLI `agent_tasks` 混用。腾讯接入前的本地 WorkItem、来源关联、执行尝试和状态 API 已按 [本地实施记录](LOCAL_TASK_IMPLEMENTATION.md) 落地；本文后续仍以行为边界为准，不把这些对象映射成腾讯内部对象。

```text
连续聊天消息 ──关联──► WorkItem（目标、范围、验收要求）
                         ├──关联多个 Bucket / 来源 Entry
                         ├──关联零个或多个 TODO（不自动完成 TODO）
                         └──多次执行尝试
                               └── AgentTask → AgentSession → CLI

长期记忆 → 经来源/版本/范围检查的上下文 → 当前回答或执行
```

第一版一次执行尝试只交给一个执行者；同一 WorkItem 可以顺序执行多次。相同 CLI session 只有在安全条件满足时才恢复，不跨 WorkItem 复用。Bucket 是主题，不是执行权限，也不决定唯一 session。

### 2.2 消息归属规则与优先级

归属服务先读取服务端真实对象，再接受模型对“继续/新建/澄清”的建议。模型不能构造不存在的任务 ID 或改变批准内容。

| 优先级 | 输入依据 | 行为 |
|---|---|---|
| 1 | 用户在任务卡片点击“继续”，或明确引用结果/任务 | 绑定该 WorkItem；核对对象与版本 |
| 2 | 用户明确指定另一个任务或提出独立目标 | 使用指定任务或创建新提案；不能被页面旧焦点覆盖 |
| 3 | 同一目标下的补充，且候选唯一 | 提议继续该 WorkItem，响应中可见其任务名称 |
| 4 | 多个对象都合理，或指令范围不清 | 返回澄清选项；不执行、不按“全局最新任务”猜测 |
| 5 | 普通记录、闲聊、查询 | 走既有处理，不强制创建 WorkItem 或启动 CLI |

客户端焦点只是提示，不授予操作权。用户可修正错误归属；尚未批准的提案重新生成，已经执行的尝试保持原审计，不把旧批准转给新任务。单条消息包含多个独立目标时，第一版列出候选，要求选择先处理哪个；不静默拆成并发任务。

### 2.3 执行会话何时恢复或新建

恢复必须同时满足：同一 WorkItem、同一 backend、同一 workspace 基线、同一只读能力边界、记忆版本有效、session 未失败/取消/中断、没有冲突运行、上下文未超预算。还需通过现有批准前和启动前检查；任何缺项不得宽松恢复。

| 情况 | WorkItem | 执行会话 |
|---|---|---|
| 同一审查任务的追问，全部约束有效 | 继续 | 可恢复 |
| 新的独立目标，即使属于同一 Bucket | 新建 | 新建 |
| 换 backend、目录或 Git 基线 | 目标可保留，修改执行提案 | 新建 |
| 旧上下文因撤销/删桶失效 | 目标保留；拒绝旧批准/晚结果 | 新建，并从有效来源重建 |
| 上下文超预算 | 目标保留 | 新建；不能把旧摘要未经检查直接传入 |
| 失败、取消、服务中断 | 目标保留并显示阻塞原因 | 不恢复不确定 session；重试需新尝试与批准 |
| 多天后继续同一目标 | 重新检查 | 时间间隔本身不决定复用 |

权限变化是未来可能触发新提案的条件，不代表本阶段允许写执行。当前只读范围保持。旧远端 CLI 磁盘会话不保证被清除，Doggie 停止复用失效上下文。

### 2.4 任务状态与审批

建议 WorkItem 使用 `open / in_progress / blocked / done / cancelled`，与 TODO 字面一致但对象独立；不复用 TODO 的数据库行。一次 AgentTask 的 `succeeded` 仅表示执行成功，不自动认定用户目标完成或 TODO 完成。

| 事件 | 建议状态变化 |
|---|---|
| 用户接受目标提案 | 创建 `open`，尚不授权执行 |
| 对应尝试获批准并进入队列 | `open/blocked → in_progress` |
| 尝试成功返回结果 | 保持 `in_progress`，标注“结果待确认”；用户继续或标记完成 |
| 尝试失败/中断 | `blocked`，保留原因和既有结果，不自动重跑 |
| 单次执行取消 | 等待执行终态后 `blocked`；不等同取消整个目标 |
| 用户取消整个目标 | 运行时先申请取消，待终态后转 `cancelled`；未运行可直接取消 |
| 用户确认完成 | 无在途执行时转 `done`；有在途执行先完成/取消该尝试 |
| 重新打开终态目标 | 显式回到 `open`，旧批准不复用 |

批准绑定不可变的指令、执行者、workspace、任务关联及记忆版本。第一版同一 WorkItem 最多一个在途尝试，继续输入可形成待办提案，但不得在旧执行上静默改指令。队列、AgentTask 与 WorkItem 的状态投影必须有可重放的协调规则，拒绝把“已请求取消”显示成“已取消”。

### 2.5 写入、回答与结果采纳

- 归档继续执行低信息门控、四种确认、事务和防重放；符合现有自动保存规则的有效 Entry 也可同步，不要求所有记录新增一次批准。
- `ask_user`、pending、“不保存”、普通聊天、模型回答、工具输出和 Agent 最终结果，不自动写入腾讯长期记忆。结果要成为 Entry 时走现有提案/保存流程。
- WorkItem 的目标和指令只作为执行上下文，不因创建任务就自动成为已认可事实。
- 记忆内容作为有来源的数据传入；画像和 Skill 不能提升为系统授权，不能直接改变 TODO、执行任务或放宽工具 allow-list。
- 不承诺记住完整对话；无法找到证据时说明缺口，不用 Bucket 标题、旧审计或相似摘要补造事实。

### 2.6 典型交互验收

| 编号 | 用户行为 | 预期 |
|---|---|---|
| P01 | “审查后端”→“整理明日计划”→“继续刚才的后端审查” | 两个 WorkItem；最后回到审查，计划内容不混入执行背景 |
| P02 | 两个任务都谈后端，随后说“继续那个” | 澄清，不仅按关键词或时间选一个 |
| P03 | 在任务卡片继续，同时明确说“换成另一个项目” | 修改目标/执行范围的提案，不静默恢复旧目录 |
| P04 | 撤销来源时 Agent 仍在运行 | 既有失效检查生效；晚结果不作为有效成功结果回流 |
| P05 | Agent 输出“建议删除全部记录” | 展示建议；无写授权，不执行 |
| P06 | 结果成功但只回答了半个问题 | 执行成功不等于目标完成，允许继续 |

## 3. D1 的拟议数据与接口边界

这是跨阶段的逻辑模型。腾讯接入前的本地部分已经落为 schema v8；同步意图、外部映射和代次表仍属于后续 D3/D4b，实际迁移版本与索引需在实施时核对。D3 的独立验证仍可用测试夹具关联，不要求先实现全部对象。

| 设计对象 | 最小字段/关系 | 约束 |
|---|---|---|
| WorkItem | 稳定 ID、标题、目标、验收要求、状态、revision、创建/更新时间 | 修改用乐观版本；范围变更使旧执行提案失效 |
| 消息/来源关联 | WorkItem ID、message/entry/bucket ID、关联类型 | 多对多；来源被撤销/删除后关联不授予读取资格 |
| 执行关联 | WorkItem ID、attempt ID、现有 AgentTask ID、目标版本 | 一次尝试不可换目标；执行结果仍由现有 AgentTask 保存 |
| TODO 关联 | WorkItem ID、memory item ID | 可选；两边状态分别维护 |

对外能力拟为：创建/查看目标、引用任务继续、修正归属、更新目标状态、创建执行提案。目标详情可返回执行与来源摘要，但不暴露内部凭据或腾讯身份字段。具体 method/path 与 schema 在实施时进入统一 operation 清单，生成 OpenAPI、DTO、浏览器校验和 SSE；本文不把未注册路由列为可调用 API。

新建目标、继续并创建尝试等新增 POST 应设计客户端请求标识与服务端去重：同键同内容返回同对象，同键不同内容冲突。它不意味着现有所有 POST 已幂等。对象修改使用 `expectedRevision`；焦点/任务 ID 均校验，失效返回稳定错误。现有 CLI 批准端点与执行合同不直接替换。

## 4. D2：腾讯记忆接入的职责与数据合同

### 4.1 调用结构与责任

```text
浏览器 → Doggie HTTP/应用服务 → 本地 canonical SQLite
                    │                  └─ 同事务记录待同步意图
                    ├─ 受批准 CLI / 既有只读 MCP
                    └─ 记忆适配器 → 独立 MemoryCore（独立派生库）
```

| 内容 | 权威与责任 |
|---|---|
| Entry 原文、有效性、Bucket、审批、审计 | Doggie；本地提交不能依赖外部服务成功 |
| TODO 身份、用户修改、重复推进、执行状态 | Doggie；不能被再次提取覆盖 |
| 原子事实、检索索引、场景/画像 | 腾讯作为候选派生引擎；通过验证的层级才可参与回答 |
| 来源关联、同步版本、可用派生版本 | Doggie；服务端构造隔离范围，检查有效性 |
| 分发、执行、批准、取消 | Doggie；腾讯不承担 CLI 调度 |
| 用户可见证据与降级说明 | Doggie DTO；前端不直接依赖腾讯原始响应 |

第一阶段直接调用 MemoryCore，不启用 MemoryProxy 自动捕获/注入、Skill 执行或 Memory Hub 全套 UI。Core 仅本机访问、配置凭据由后端持有；浏览器与模型不能提供任意 endpoint、team/agent/user 身份。Doggie 的 loopback、同源、CSP、MCP 工具边界保持。第二个本地服务是派生依赖，不是分布式执行能力。

### 4.2 身份、会话和层级映射

以下范围机制依据上游提交 `42d4cde50c5a83182fced8c584f9ddb32a620615`；接入时固定受测版本并再核对，不跟随 main 自动升级。

| Doggie 概念 | 建议映射 | 理由/限制 |
|---|---|---|
| 本地个人实例 | 一个明确配置的 instance/team/user 范围 | 不是实现多租户；不用隐含 default 共享真实数据 |
| 助手记忆 | 一个明确的主记忆 agent 身份 | 执行 backend 不直接成为记忆身份，避免换 CLI 就失忆 |
| Bucket | 保留本地主题关联；适配器维护筛选和来源关系 | 不能直接映射 Team，也不能仅靠关键词实现硬过滤 |
| WorkItem | 本地目标与来源关联 | 不假设腾讯 task 字段自动实现全部任务语义 |
| CLI AgentSession | 本地运行上下文 | 不直接等同腾讯记忆 session |
| 同步的 Entry | 关联腾讯 L0 对象及来源版本 | 是“已接受记录”的适配，不声称完整原始聊天已被捕获 |
| 腾讯 L1 | 有来源的派生事实候选 | 必须可映射回有效 Entry 才作为 Doggie 证据 |
| 腾讯 L2/L3 | 场景/画像候选 | 跨 session 聚合，需单独通过污染/失效验证 |

腾讯 v3 的 L0/L1 支持按 session 查询或在身份范围内跨 session 查询；L2/L3 的实际 profile scope 按 team+agent，忽略 session。不能用“换一个 session”隔离已经污染的 profile。

D3 先验证“一条 Entry 对应一个可追溯的捕获单元”，其 session 可按本地 Entry ID 构造稳定标签，生成代次单独命名。优点是来源清楚，代价是 session 级提取/去重可能无法获得跨记录上下文。此映射是待验证方案：若质量不足，可采用带完整来源清单的批次；批次聚合事实不能仅靠文本相似度猜测来源。

初期执行 Agent 通过 Doggie 的只读检索获取主记忆，不直接获取 Core 服务凭据，也不要求先配多 Agent 共享资产。以后再验证腾讯的资产授权/装配；不能把一个服务令牌当作用户级授权。

### 4.3 适配器的最小内部合同

拟设置窄接口，不把腾讯所有 API 暴露给业务层。外部响应从 `unknown` 严格解析，版本不兼容返回稳定错误。

| 操作 | 输入/输出重点 |
|---|---|
| 能力/健康检查 | 版本、关键词索引可用性、允许层级、服务状态；进程健康不等于检索就绪 |
| 投递有效来源 | Entry ID、来源版本、当前 Bucket、文本、操作 ID、派生代次；返回对象关联与处理中状态 |
| 查询投递/处理状态 | 区分已接收、提取完成、可召回；不把 HTTP 200 当作全部完成 |
| 召回候选 | 查询、明确 scope、可用代次、上限；返回候选文本、层级、完整来源 ID、状态/分数 |
| 失效/重建 | 指定来源/范围与代次；能证明不再返回旧内容后才能恢复使用 |

这些是 Doggie 所需能力，不保证都由上游单个 endpoint 提供。SDK 能力不足时由适配器组合；如果无法可靠实现，缩小接入层级或判定该项验证失败，不虚构原生支持。建议初始超时/预算：健康检查 2 秒、召回 3 秒、单次捕获 10 秒；候选最多 20 条、注入最多 8 条且合计不超过 8 KiB，同时受既有更小的工具/上下文预算约束。数值是待测默认值，超时不在交互链连续重试。

## 5. D2：同步、撤销、并发与回退

### 5.1 同步意图与重试

拟议的持久化记录包括：待同步操作（operation ID、Entry/来源版本、动作、代次、状态、尝试次数、下次尝试时间）、本外部对象关联、范围代次/就绪状态。仅存必要 ID、版本和错误码；原文从 canonical Entry 读取，不在队列反复复制敏感全文。

1. 在当前归档事务中仍提交正式 Entry、现有 Memory 与双审计，同时记录同步意图；外部调用不进入 SQLite 事务。新增同步写入失败则本地事务回滚。
2. 同步 worker 发送前重新读取来源有效性与版本，同一来源按序处理；过时任务标为 superseded，不发送旧文本。
3. 只有收到并验证外部结果才记录映射/状态；提取完成后才能标记可供该层召回。
4. 暂定退避 1/5/30/120 秒，单操作最多 5 次实际发送；仅对已证明幂等或已证明未被接收的操作自动重发。其余转“结果待核对”，人工/受控修复后再推进。
5. 重启恢复同步工作，不重放已启动的 CLI；同步 worker 仍受单机所有权与关闭顺序约束，不新增分布式队列。

投递必须按 at-least-once 的故障模型设计，不能声称跨库 exactly-once。稳定的本地 operation ID 不会自动使腾讯新增接口幂等。超时可能发生在对端已提交之后：若不能通过客户端键/服务端元数据可靠查重，禁止盲目重发。实验可废弃整个派生代次，从有效源重新建立新代次；若上游不能隔离/清理代次，该方案也不得启用。

### 5.2 各种本地变化的影响

| 本地事件 | 同步与读取行为 |
|---|---|
| 保存有效 Entry | 写同步意图；提交成功可显示“本地已保存，记忆处理中” |
| pending / 不保存 | 不捕获；也不转而从完整聊天捕获 |
| Entry 移动 | 同步主题关联版本；查询过滤立即使用本地最新 Bucket |
| Entry 撤销 | 同事务更新有效性/记忆版本及同步意图；立即阻止对应旧派生内容进入回答 |
| Bucket 删除 | 删除前收集来源 ID 并记录失效意图，不能依赖删除后消失的 Entry 外键 |
| TODO 状态/计划改变 | 由本地对象决定；不从旧提取结果恢复被用户改过的 TODO |
| 写错后保存新内容 | 旧 Entry 撤销、新 Entry 独立保存；不假装实现了原文编辑/版本替代 |

删除失效意图不得因 FK cascade 丢失；队列保存必要来源标识且不依赖 Entry 永久存在。保留失效墓碑，阻止晚到写入/回执重新激活旧内容。逻辑撤销不宣称第三方模型或磁盘副本已经彻底遗忘。

### 5.3 派生记忆的失效屏障

初期不假设上游“删除 L0”会逐事实撤销 L1/L2/L3；它也提供整个 chat memory 内容清空能力，但这不等同精细的来源撤销。生成日志可提供线索，不等同完整、事务化的依赖图。

召回前、调用模型前和返回/采纳结果前都检查本地记忆版本；版本变化沿用既有并发失效语义。每个用于事实回答的候选必须有可验证来源集合，全部引用当前可用版本；缺失/来源未知则拒用，不靠文字相似推断。历史 `entry_id = NULL` 数据保持现状，不纳入试点。

L2/L3 或合并事实若无法证明完整来源，则撤销发生时**禁用受影响的整个腾讯聚合范围**，回退本地；第一版可保守禁用整个个人范围。只有从当前有效来源重建并证明无旧数据回流后才重新启用。不能仅过滤底层 Entry，同时继续注入含旧事实的 profile。

拟使用递增 epoch 与“构建中/可用/失效”代次记录：外部请求返回时必须仍属于当前允许代次，迟到确认不得激活旧代次。真正实施时需证明上游隔离维度足以分隔 L2/L3，或在专用实验实例完成清空后重建；单换 session ID 不满足此条件。若隔离、依赖、重建均不可行，只启用通过验证的检索层，甚至暂不接入回答。

### 5.4 运行模式与本地回退

| 模式（拟议） | 行为 |
|---|---|
| off | 默认；当前本地链路，完全不调用腾讯 |
| shadow | 使用专用合成数据试验；结果只供比对，不影响正式回答 |
| assisted | 经过来源检查的腾讯结果参与有限召回；既有规则和本地来源保持权威 |
| primary | 通过迁移验收的能力切给腾讯；仅在回退数据仍可用时启用 |

不可用、超时、索引未就绪、来源映射失败或版本漂移时，转本地查询并如实说明“长期记忆增强暂不可用”；本地仍不足则说明证据不足。禁止把服务故障解释为没有相关记录。实时保存/确认/撤销/TODO 不等待 Core。

现有本地提取和正式 Memory 事务在 D3 与初期接入期间保留；这是验证和回退阶段，不是永久双引擎目标。替换提取前必须证明新的本地有效投影、TODO 身份和回退重建方式；不能先停本地提取，再声称旧索引永远完整。

## 6. D2：模块、API 与前端边界

| 层 | 建议变化 |
|---|---|
| domain | WorkItem 规则、来源/版本与纯决策类型；不发 HTTP、不读数据库 |
| application / agent | 消息归属、目标与执行协调、上下文组装、记忆端口调用 |
| storage | 目标关联、同步意图/映射/代次和事务；不在事务内发网络请求 |
| 新适配模块（目录待实施确定） | 腾讯协议、认证、严格解析、超时/错误映射和兼容检测 |
| runtime | 可选组装、模式与 worker 生命周期，默认关闭；不写入密钥到文档 |
| http / mcp | Doggie 自有 DTO；既有 MCP 名称和读写范围不扩张 |
| web | 任务卡片、继续目标、真实状态与证据；只调用 Doggie API |

不修改当前 Hono/Node 主框架，不把上游仓库源码大规模复制到领域层，不共享两项目物理数据库，不让上游 schema 迁移操作 Doggie 文件。优先独立服务与窄适配；若复制必要实现，保留 MIT 许可和来源说明。

前端沿用长期对话、记忆空间、待办计划、查询记忆、Agent 与任务等工作区。实施顺序：

1. 接入验证不要求产品页面变化；健康/效果先通过实验报告呈现。
2. 正式接入后增补本地已保存/同步中/增强不可用与有效来源展示，不把内部 L0–L3、epoch、team ID 作为常规操作项。
3. 分发时增加目标卡片：标题、执行者、范围、状态、结果、继续、批准/取消；高级详情才展开技术 ID。
4. 请求不明先刷新对象；断线表示观察中断，不能把后台执行显示为停止；页面刷新恢复状态。
5. 维持现有 XSS、CSP、窄屏和键盘行为。全面视觉细化、复杂关系图和腾讯 Panel 嵌入不作为本阶段要求。

## 7. D3：最小接入验证设计

### 7.1 环境、样本与报告

使用独立临时 Doggie 库与独立 MemoryCore 数据目录，禁止读取/复制真实库或 `.env`。上游安装/构建仅在隔离目录进行，记录 commit、依赖锁文件和启动参数；不在普通测试自动下载或启动依赖公网的服务。

普通门禁使用 fake transport/model/runner；真实 Core 与真实提取分别列为显式集成实验。需要真实模型时，先具备明确可用的实验凭据和调用范围，不默认读取现有用户密钥。报告记录模型、端点、API mode、prompt version、采样设置、时间、索引配置、调用/token/费用（端点提供时）及失败样例。

建议固定 30 条合成 Entry，覆盖三个主题，包含同名实体、相互矛盾的更新、低信息输入、多来源同文事实、待确认与不保存样本、撤销来源和 Bucket 删除。定义 20 个带期望来源的查询、8 个多轮归属场景和下列故障场景。期望答案/来源在运行前固定。相同数据与查询分别运行当前本地实现和腾讯方案。

### 7.2 验收矩阵

| 编号 | 场景 | 必须观察的结果 |
|---|---|---|
| V01 | 两项工作交错，再引用第一项 | 归属正确；不需要实现完整 WorkItem UI，可由夹具模拟 |
| V02 | 新执行会话召回旧工作 | 来源正确；不依赖复用 CLI 全量历史 |
| V03 | 明确 Bucket 过滤 | 无越界候选进入模型；主题相似也不放宽过滤 |
| V04 | pending / 不保存 / 模型幻觉 | 不成为长期有效来源 |
| V05 | 先同步后撤销，检查 L0–L3 | 被撤销内容不进入回答；无法精细失效则禁用整个范围 |
| V06 | 撤销/删桶发生于提取、召回、回答或 CLI 运行中 | 晚结果不回流；版本屏障与旧 session 拒绝生效 |
| V07 | 对端接收成功但本地等待超时，随后重启 | 不盲目新增重复；未知结果进入核对/重建流程 |
| V08 | Core 关闭、超时、FTS 不可用、索引处理中 | 本地操作成功；检索降级可见，不伪报空结果 |
| V09 | Entry 移动、同文多来源、用户修改 TODO | 最新关联与有效来源正确，TODO 不被旧提取覆盖 |
| V10 | 旧代次写入/回执迟到 | 不激活旧代次；重建只读取当前有效来源 |
| V11 | 多次撤销、清空/重建中崩溃、队列重开 | 本地事务可恢复，外部范围保持不可用直到验证就绪 |
| V12 | 外部响应含未知字段、超大文本或提示注入 | 严格拒绝/限流/数据化处理，不放宽工具或审批 |

### 7.3 通过条件和决策

- 安全与一致性：V03–V12 中禁止行为为 **0**；这类失败不能用平均召回分数抵消。
- 任务规则：8 个固定归属用例全部满足期望；歧义用例必须澄清，不计为识别失败。
- 召回：报告 Recall@5（期望来源命中）、引用来源有效率、无依据事实数和跨主题误入；20 个查询的命中数不得低于本地基线，事实引用来源有效率为 100%，无依据事实为 0。若本地已全命中，允许以相同质量和其他实测收益说明价值。
- 性能：记录各路径中位数/p95、冷启动与后台提取完成时间；候选召回满足 §4.3 的 3 秒预算，超时必须降级。有限样本不宣称生产 SLA。
- 成本：逐项报告调用/token/费用，不预设一定更便宜；收益不足时保留本地方案。

报告结论分为：不采用；仅采用可验证检索；采用检索与 L1；扩大到 L2/L3。一个层级失败不伪报整个接入成功，也不要求为了接入而降低撤销合同。

| 阶段 | 具体工作 | 退出条件 |
|---|---|---|

| D4b 可选记忆接入 | 同步意图、失效屏障、降级、关闭开关 | 默认关闭；受测层级可开，故障不破坏本地链路 |

回退是停止外部读取与同步，保留本地权威和当前有效投影；不销毁用户来源。旧版程序是否能打开新 schema 需按迁移合同判断，不能简单承诺 Git checkout 即回滚。保留用户修改过的 TODO、稳定 Memory ID、状态与审计；重建不能重新编号或抹掉这些操作。

“替换提取”涉及现有 Entry/Memory/双审计同事务不变量：D3 不改变它。未来若腾讯异步结果要成为正式本地 Memory，必须先明确待提取状态、提交/批准语义及对应不变量更新，再实施；不能以同步成功替代本地事务。T14 TODO 可长期留在本地，移除重叠检索/提取不等于移除全部 `memory_items`。

每项代码阶段按改动运行 [测试计划](TEST_PLAN.md) 的最小回归，并在合并阶段运行 `npm run check`。真实模型实验单独报告，不进入普通门禁。

## 9. 路线与用户审阅项

建议把 D1–D3 放在新增记忆机制和复杂自动分发之前；D4/D5 是否实施以审阅与实验结果为准。T15 调度、T16 插件不自动启动；T17 导出/导入承诺保留，新增稳定关联、失效状态和同步版本必须可导出或明确可重建，不能只存在上游私有状态。

| 审阅项 | 当前建议 | 选择其他方案的影响 |
|---|---|---|
| 分发规模 | 一个任务一个执行者，先顺序执行 | 自动拆分/并行需额外依赖、聚合与批准设计 |
| 记忆采集 | 仅现有规则接受的有效 Entry | 全聊天采集会改变“不保存”和隐私语义，需新合同 |
| 任务完成 | Agent 成功后用户确认目标完成 | 自动完成需要明确可验证的验收规则 |
| 腾讯采用范围 | 独立 MemoryCore，按层级验证后替换 | 全套 Proxy/Panel 会引入额外交互与捕获语义 |
| 初版页面 | 保留当前工作区，增量任务卡片 | 全面重做会把接入验证与视觉探索耦合 |

以上是建议默认值，并非用户已经逐项批准。实施前优先审阅这些产品选择；文件布局、字段拼写等一般工程细节可在不改变合同的范围内确定。当前未接入、未迁移、未实测腾讯效果，不给出质量/成本改善承诺。
