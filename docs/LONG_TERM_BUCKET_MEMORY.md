# 长期 Bucket 记忆设计

## 1. 核心定位

Bucket 不是聊天记录、文件夹或无限增长的长文本，而是一个持续存在的事务档案。它负责聚合同一目标或上下文中的原始输入、当前状态、待办、证据、时间线和决策。

```text
Bucket = 原始历史 + 当前摘要 + 结构化状态 + 可追溯关系
```

长期使用时，Bucket 的底层内容可以持续增长，但每次提供给用户或 LLM 的默认上下文必须保持有限、清晰且与当前问题相关。

## 2. 分层记忆模型

### 原始记忆：Entry

每次用户输入保存为独立 `Entry`，`raw_text` 原则上不可覆盖。LLM 提取错误时，应通过原文重新提取或写入纠错记录，而不是修改历史事实。

### 当前记忆：Bucket.summary

`Bucket.summary` 是可重建的“当前状态缓存”，应简要包含：

- 事务目标；
- 当前阶段；
- 关键有效决策；
- 阻塞事项与下一步。

摘要不是历史全集，不应简单拼接全部 Entry。

### 结构化记忆

- `Todo`：尚需完成的具体动作；
- `Evidence`：日志、指标、观察和测试结果等依据；
- `TimelineEvent`：某个时间发生的事件；
- `Decision`：已经做出的选择或处置；
- `Entry`：所有结构化事实的来源。

每条派生记录应同时保留 `bucket_id` 和尽可能明确的 `entry_id`，确保可以追溯到用户原话。

## 3. Bucket 持续积累示例

以 `个人事务 Agent MVP`（`type=task`）为例：

```text
Entry #1：计划使用 SQLite 和 Streamlit 开发 MVP
  ├─ Todo：搭建 SQLite 数据层
  └─ Decision：MVP 使用 SQLite 和 Streamlit

Entry #2：数据库模型完成，下一步完善分类 Schema
  ├─ Todo“搭建 SQLite 数据层”：open → done
  ├─ Todo：完善分类结果 Schema
  └─ Timeline：完成数据库基础模型

Entry #3：不能直接相信 LLM 自报置信度，先建立人工标注集
  ├─ Todo：建立分类标注集
  ├─ Todo：统计置信度区间准确率
  └─ Decision：使用真实评估结果校准 confidence
```

此时 Bucket 的滚动摘要可以更新为：

> 数据库与结构化 Schema 已完成，当前优先建立分类评估集并校准置信度，之后再打通提取和自动归档闭环。

原始 Entry 继续完整保存，但默认界面只突出摘要、开放 Todo、有效 Decision 和最近时间线。

## 4. 控制冗杂的规则

1. **摘要压缩而不删除历史**：每次追加后更新当前摘要，详细过程保留在 Entry 和 Timeline 中。
2. **Todo 更新优先于重复创建**：将“需要补复盘”“复盘还没写”等表述匹配到同一 Todo，并更新状态或截止时间。
3. **Evidence 去重**：MVP 可先对清理后的同 Bucket 文本做精确去重；以后再增加出现次数和来源列表。
4. **保留决策演变**：新决策替代旧决策时，不删除旧记录；长期可增加 `status` 和 `supersedes_id`。
5. **冷热数据分离**：默认加载摘要、开放 Todo、有效 Decision、最近时间线和少量最近 Entry；旧内容仅在查询相关历史时召回。
6. **摘要视为缓存**：摘要和提取结果可以重建，原始 Entry 才是事实来源。

## 5. 何时拆分 Bucket

不应只根据 Entry 数量机械拆分。出现以下情况时，应优先创建新 Bucket 并保留关联：

- 新内容拥有不同目标或独立完成条件；
- 内容类型明显变化，例如长期开发任务中发生独立线上故障；
- 新事务有独立负责人、时间线或生命周期；
- 当前摘要已经无法用几句话清楚说明；
- 用户明确要求“新开一个”“单独记录”或“另一个问题”。

例如将 `个人事务 Agent MVP`、`分类接口 500 故障` 和 `Agent 商业化方案` 分成三个 Bucket，而不是堆入同一个大 Bucket。

## 6. 生命周期与上下文构造

Bucket 状态建议按以下方式使用：

```text
active → paused → active
active → done → archived
```

- `active`：正在推进；
- `paused`：暂时停止但可能恢复；
- `done`：目标已完成；
- `archived`：默认不参与近期分类候选，但仍可搜索。

发送给 LLM 的内容不应是全部历史，而应构造有限的记忆上下文：

```text
当前摘要
+ 开放 Todo
+ 当前有效 Decision
+ 最近 TimelineEvent
+ 最近若干 Entry
+ 根据本次问题检索出的历史 Entry
```

“最近内容”维持连续性，“相关历史”负责找回几个月前的重要决定。

## 7. 当前项目的实现顺序

当前仓库已经具备 Bucket、Entry、Todo、Evidence、TimelineEvent 和 Decision 模型，但自动提取入库、滚动摘要和去重尚未完整实现。建议依次完成：

1. 实现 `save_extraction()`，在同一事务中保存 Entry 及派生记录；
2. 保证派生记录关联来源 `entry_id`；
3. 实现 Bucket 滚动摘要；
4. 实现 Todo 状态匹配和简单 Evidence 去重；
5. 构造有限的冷热记忆上下文；
6. 数据量增长后再引入语义检索、摘要快照、Bucket 关联和决策替代关系。

## 8. 必须长期坚持的原则

```text
原始输入永不丢失；
结构化状态持续更新；
当前摘要保持简洁；
重复事实避免堆积；
新目标及时拆分 Bucket；
历史内容按需检索；
任何结论都能追溯到 Entry。
```
