# D3.4 故障与撤销：实施计划

日期：2026-11-18。目标是在 D3 的 L0/L1 隔离报告之后，先验证阻止生产采用的正确性问题：未知写入、撤销期间的晚结果、代次隔离与本地降级。独立实验放在 `scripts/d3/`；只用合成来源、临时 SQLite 和 fake transport。已有授权只适用于上一轮模型实验；本步调用真实模型 0 次。Doggie 生产 API、生产数据库、部署和 UI 均不调整。

## 实现顺序与验收条件

1. **保存状态再发送。** 用单执行器 SQLite 实验台记录代次、来源版本和 `sending`/`acked`，同来源同代次只允许一次发送。对端错误或未确认结果隔离整代；重开时未完成构建保持隔离，即使上一部分已收到回执。用真实临时 SQLite 验证重开和重建中断，fake Core 保留“已写入但未收到回执”的旧记录。
2. **重新验证再启用。** 新代次使用不同 team scope；只从当前有效来源构建。从 Core 回读完整 L0 成员并核对来源集合、版本、身份与内容后才能启用。旧回执、旧验证结果和旧快照不能激活任何代次。当前实验不清理外部旧物理记录，要求它们即使残留也不得影响新代次。
3. **在读取和使用时做两次判定。** 复用现有 L0 来源闸门；等待 Core 结果后，以及将结果交给回答逻辑前后重新检查来源和代次。外部只提供候选；Bucket、Entry 状态和有效版本取自本地。明确区分“正常无命中”和“已回退本地”。插入的文字只作为证据数据传入回答回调，无工具或审批能力。L1/L2/L3 不进入此路径。
4. **执行并记录分层结果。** `npm run d3:matrix` 运行离线矩阵，`npm run check` 运行完整门禁。结果逐项标注是实验适配器、现有 Doggie 回归，还是真实固定上游证据；未运行的场景保持待验证。满足本轮条件只代表可以做下一轮固定上游验证。

上游验证时继续固定已选 commit，使用现有 `d3:l0` 隔离规则。优先复核 team scope 隔离、L0 回读和旧代次写入；若上游历史 checkout 或依赖不可用，保留该项未运行，不能把 fake 结果替代真上游证据。

- `npm run d3:matrix`：新增 10 个故障测试，与既有 9 个来源/协议测试一起执行。V02–V12 都有上表限定的 L0 实验证据；V01 仍只有确定性归属规则。V11 使用独立 Node 进程写入部分状态并退出，随后用实际 SQLite 重新打开；没有模拟真实 Core 掉电。
