# 相似产品与开源项目调研

> 说明：本文件用于产品设计参考，不代表这些产品与本项目定位完全相同。调研日期：2026-08-01。

## 1. 参考维度

本项目不是普通聊天机器人，也不是传统笔记工具。调研时重点看这些问题：

1. 如何降低用户整理成本。
2. 如何表达信息对象和上下文。
3. 如何支持检索、关联和长期记忆。
4. 如何把 AI 嵌入到用户工作流，而不是只做问答。
5. 开源项目如何处理本地知识库、对话记忆和 Agent 状态。

## 2. 市场产品参考

### 2.1 Mem

官网：<https://get.mem.ai/>

可借鉴点：

- 强调快速捕获和 AI 辅助找回。
- 用户不需要一开始就完美分类。
- 适合“先丢进去，后面再找”的工作流。

对本项目的启发：

- 输入体验要极简，不要让用户先选类型。
- 归档后必须能找回，否则“自动整理”价值不成立。
- 应重视自动生成标题、摘要和关联。

需要避免：

- 如果只做搜索和聊天，bucket 的“可追踪工作对象”特色会被削弱。

### 2.2 Capacities

官网：<https://capacities.io/>

可借鉴点：

- 以 object/object type 的方式组织知识，而不是只有文件夹和页面。
- 同一类对象可以有稳定字段。
- 对长期知识管理更结构化。

对本项目的启发：

- bucket 可以看成一种动态 object。
- incident、experiment、meeting 等类型可以有默认字段模板。
- 对象化结构比单纯 Markdown 更适合后续做视图、过滤和统计。

需要避免：

- 第一版不要让用户手动设计 object schema，否则新手门槛高。

### 2.3 Tana

官网：<https://tana.inc/>

可借鉴点：

- 节点化信息组织。
- supertags 让普通内容变成带结构的对象。
- 适合从松散笔记逐步结构化。

对本项目的启发：

- bucket type 类似轻量 supertag。
- 用户输入可以先是普通文本，系统再自动打类型和抽字段。
- 同一条内容可以关联多个 bucket，而不是只能放进一个文件夹。

需要避免：

- 不要一开始做复杂 graph UI。MVP 用列表和详情页即可。

### 2.4 Notion AI / Notion

官网：<https://www.notion.com/product/ai>

可借鉴点：

- AI 嵌入文档、知识库、项目和任务场景。
- 输出不是只有聊天，还可以变成文档、总结和行动项。

对本项目的启发：

- bucket 详情页可以输出文档化视图。
- meeting、incident、experiment 应该有不同的“视图模板”。
- AI 结果要落到可编辑资产，而不是临时回复。

需要避免：

- 不要一开始复制完整协作文档系统。本项目重点是自动归档和工作记忆。

### 2.5 Reflect

官网：<https://reflect.app/>

可借鉴点：

- 强调快速记录、双向链接、日记式输入和 AI 辅助。
- 笔记之间可以通过链接形成网络。

对本项目的启发：

- 可以支持“今日输入流”，再由系统自动沉淀到 bucket。
- bucket 间关联可以逐步生成。
- 每天的输入也可以形成 daily log，方便回顾。

需要避免：

- 如果过度依赖手动链接，会违背“自动整理”的目标。

## 3. 开源项目参考

### 3.1 Khoj

GitHub：<https://github.com/khoj-ai/khoj>

定位参考：个人 AI 助手、可连接个人知识源，并支持搜索/问答等能力。

可借鉴点：

- 本地/个人知识助手方向。
- 对多来源知识检索有参考价值。
- 适合后续学习如何做个人知识库问答。

对本项目的启发：

- 未来可以把 bucket、entry、文档作为可检索知识源。
- 需要处理“问历史上下文”和“新输入归档”两类意图。

### 3.2 AnythingLLM

GitHub：<https://github.com/Mintplex-Labs/anything-llm>

定位参考：面向文档和知识库的 AI 应用平台。

可借鉴点：

- workspace 概念。
- 文档上传、检索增强、聊天界面。
- 部署和用户可控性。

对本项目的启发：

- bucket 可以被看作更细粒度的 workspace。
- 后续支持文件/截图时，可以借鉴“把资料放进知识空间”的思路。

需要避免：

- 本项目不是“上传文档然后聊天”，而是“持续捕获工作碎片并组织为事项”。

### 3.3 Onyx，原 Danswer

GitHub：<https://github.com/onyx-dot-app/onyx>

定位参考：企业知识检索和 AI 助手。

可借鉴点：

- 连接多数据源。
- 混合搜索和权限意识。
- 面向组织知识的问答。

对本项目的启发：

- 当未来做团队版时，需要考虑权限、连接器和来源引用。
- 搜索不仅要语义相似，也要支持关键词和过滤。

MVP 暂不做：

- 企业连接器。
- 权限系统。
- 多租户。

### 3.4 mem0

GitHub：<https://github.com/mem0ai/mem0>

定位参考：AI Agent 的记忆层。

可借鉴点：

- 将记忆作为独立层，而不是塞进 prompt。
- 支持长期记忆抽取、更新和检索。

对本项目的启发：

- 用户偏好、长期稳定事实、纠错习惯可以进入 memory layer。
- entry 与 bucket 是工作记忆，user_preferences 是行为记忆。

### 3.5 Letta

GitHub：<https://github.com/letta-ai/letta>

定位参考：带状态和长期记忆的 Agent。

可借鉴点：

- Agent 状态、记忆、工具调用分层。
- 长期运行 Agent 需要显式管理记忆和上下文。

对本项目的启发：

- 不要把所有历史直接塞进上下文窗口。
- 应该区分当前回合、当前焦点 bucket、活跃 bucket、长期偏好。

### 3.6 LangGraph

GitHub：<https://github.com/langchain-ai/langgraph>

定位参考：构建有状态 Agent 和多步骤工作流。

可借鉴点：

- 对复杂流程建模为图或状态机。
- 支持分支、循环、检查点和人工介入。

对本项目的启发：

- 后续当纠错、审批、定时总结、跨 bucket 关联变复杂时，可以考虑状态机。
- MVP 不需要直接引入，但可以用它的思想：每一步输入输出要明确。

## 5. 本项目差异化

本项目的差异化不应是“再做一个 AI 笔记工具”，而是：

> 把输入流自动沉淀为可追踪的工作对象 bucket。

重点差异：

1. 默认自动分类，而不是用户先建结构。
2. Bucket 具有生命周期，而不是静态笔记。
3. 排障、实验、会议、决策等工作场景有结构化模板。
4. 用户纠错会反向形成偏好。
5. 原始输入流和结构化工作资产同时保留。

## 6. 对 MVP 的结论

第一版应该借鉴：

- Mem 的极简捕获。
- Capacities/Tana 的对象化结构。
- Notion AI 的结构化输出和文档化视图。
- Reflect 的轻量关联和 daily log 思路。
- Khoj/AnythingLLM/Onyx 的检索意识。
- mem0/Letta 的记忆分层思想。
- LangGraph 的状态机思想，但不急着引入框架。

第一版不应该做：

- 完整知识库平台。
- 复杂 graph UI。
- 团队协作。
- 多 Agent 框架。
- 用户自定义复杂 schema。
