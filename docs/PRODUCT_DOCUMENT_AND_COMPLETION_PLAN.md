# 个人工作记忆 Agent 产品文档与后续完成规划

> 版本：v0.1  
> 日期：2026-08-03  
> 适用范围：当前本地单用户 MVP 及后续个人可用版本规划。本文是面向产品、开发与验收的综合说明；更底层的架构、数据模型和测试细节见 `docs/ARCHITECTURE.md`、`docs/DATA_MODEL.md` 和 `docs/TEST_PLAN.md`。

## 1. 产品概述

个人工作记忆 Agent 是一个面向个人工作的长期事务记忆系统。用户只需要把碎片化信息输入到一个统一入口，系统自动判断它应该追加到已有事务，创建新事务，还是先向用户确认；随后把原始输入和结构化信息保存起来，形成可追溯、可纠错、可搜索的个人工作上下文。

一句话定位：

> 一个“单入口、自动归档、可追溯纠错”的个人工作记忆 Agent。

它不试图在第一阶段替代 Notion、Obsidian、日历或任务管理工具，而是优先验证：如果输入成本足够低、整理足够自动，用户是否愿意持续把工作碎片交给系统沉淀。

## 2. 用户与使用场景

### 2.1 目标用户

第一阶段聚焦个人用户：

- 开发者：记录排障过程、实验结论、技术决策、代码方案。
- 产品经理：沉淀需求想法、用户反馈、会议结论、待办事项。
- 独立开发者/创业者：追踪多个项目、灵感、调研、复盘和风险。
- 研究或学习者：保存长期知识、阅读笔记、实验记录和阶段结论。

### 2.2 高频场景

1. **随手记录**：用户输入“支付回调 10:20 开始大量失败，第三方返回 502”，系统自动创建 incident bucket。
2. **继续上下文**：用户输入“刚才那个支付问题 10:40 切备用通道后恢复”，系统追加到同一个 bucket。
3. **结构化沉淀**：系统从原文中提取摘要、证据、时间线、决策和 TODO。
4. **低成本纠错**：如果系统归错，用户可以移动最近 entry 或明确指定目标 bucket。
5. **事后找回**：几天后用户用关键词搜索“支付 502 备用通道”，找回完整上下文。

## 3. 核心问题

传统个人工作记录工具通常要求用户主动完成整理动作：

- 先想清楚放到哪个文件夹、页面或项目。
- 手动维护标题、标签、摘要和待办。
- 在多个工具间复制会议纪要、聊天片段、日志和截图。
- 事后依赖记忆恢复上下文。

结果是大量有价值信息散落在聊天记录、临时文档、终端输出和脑子里，无法稳定复用。个人工作记忆 Agent 的机会在于把“先整理再记录”改成“先丢进来，系统再整理”。

## 4. 产品目标与非目标

### 4.1 MVP 产品目标

- 建立一个稳定的单用户本地归档闭环。
- 自动完成“追加已有 bucket / 创建新 bucket / 请求确认”的分类判断。
- 保存原始输入和结构化派生信息，保证可追溯。
- 在不确定时不强行归档，避免污染长期记忆。
- 支持用户用自然语言或界面进行基本纠错。
- 提供本地 UI、关键词搜索和基础回归测试。

### 4.2 当前非目标

- 多用户账号、团队权限和云同步。
- 移动端 App 和浏览器插件。
- 大规模文件知识库与复杂附件处理。
- 自动执行外部系统操作。
- 复杂知识图谱、语义网络或多 Agent 编排。
- 生产级安全、审计、备份和合规体系。

## 5. 核心概念

### 5.1 Bucket

Bucket 是一个持续存在的工作上下文，不是普通文件夹。它可以代表一个排障事件、需求想法、会议、实验、决策或长期知识主题。

当前支持的 bucket 类型：

| 类型 | 含义 | 典型内容 |
|---|---|---|
| `idea` | 想法或灵感 | 产品点子、优化方向、商业假设 |
| `task` | 待办事项 | 要完成的行动、交付物、跟进事项 |
| `incident` | 故障或排障 | 现象、影响、日志、修复动作、复盘 |
| `experiment` | 实验记录 | 实验条件、结果、指标、下一步 |
| `decision` | 决策记录 | 选择、理由、备选方案、影响 |
| `meeting` | 会议纪要 | 议题、结论、行动项、参会背景 |
| `knowledge` | 长期知识 | 稳定事实、方法论、学习笔记 |
| `draft` | 草稿内容 | 文档、方案、文章、表达片段 |

### 5.2 Entry

Entry 是用户的一次原始输入。原文必须长期保留，因为它是所有摘要、证据和决策的事实来源。任何结构化提取都可能出错，但不能覆盖原始事实。

### 5.3 派生结构

系统从 entry 中提取以下结构化信息：

- Summary：简短摘要。
- Todo：待办事项。
- Evidence：证据、日志、指标、引用事实。
- Timeline：带时间信息的事件。
- Decision：明确决策及理由。
- Tags：用于检索和概览的标签。

`hypotheses` 和 `entities` 已存在于 LLM 输出 Schema 中，但当前尚未持久化，应在明确使用场景后再扩展数据表。

## 6. 用户体验流程

### 6.1 普通归档流程

```text
用户输入
  ↓
读取当前焦点和活跃 bucket 作为有限候选
  ↓
LLM 输出结构化分类结果
  ↓
服务端校验 bucket_id 和置信度门控
  ↓
高置信度：创建或追加 bucket
低置信度：请求用户确认
  ↓
提取结构化信息并入库
  ↓
展示归档结果、理由、详情和纠错入口
```

### 6.2 纠错流程

```text
用户发现归档错误
  ↓
选择或表达目标 bucket
  ↓
移动 entry 及其派生记录
  ↓
记录 correction 前后快照
  ↓
重建相关 bucket 摘要
  ↓
标记对应分类审计为已纠错
```

### 6.3 找回流程

```text
用户输入关键词
  ↓
搜索标题、摘要、标签和 entry 原文
  ↓
按匹配强度返回 bucket
  ↓
用户打开详情，查看时间线、证据、TODO、决策和原文
```

## 7. 功能需求

### 7.1 已覆盖的 MVP 功能

| 模块 | 功能 | 当前状态 |
|---|---|---|
| 数据模型 | Bucket、Entry、Todo、Evidence、Timeline、Decision、Classification、Correction | 已实现 |
| 分类 | 追加、创建、询问三类动作；候选 bucket 限制；bucket_id 校验 | 已实现 |
| 风险门控 | 低置信度、多候选或异常引用时请求确认 | 已实现 |
| 提取 | 摘要、TODO、证据、时间线、决策、标签 | 已实现 |
| 归档 | 分类、审计、提取、入库单事务闭环 | 已实现 |
| 纠错 | 移动 entry、同步派生记录、记录 correction | 已实现 |
| 搜索 | SQLite 关键词搜索标题、摘要、标签和原文 | 已实现 |
| UI | Streamlit 输入、确认、详情、搜索、最近 entry 纠错 | 已实现 |
| 测试 | Pytest、mock LLM、分类和提取固定评估样例 | 已实现 |

### 7.2 下一阶段应补齐的功能

| 优先级 | 功能 | 说明 |
|---|---|---|
| P0 | 真实模型评估闭环 | 使用真实 API 报告校准分类阈值和提取质量，不把 mock 结果当作真实准确率。 |
| P0 | 导出与备份 | 本地数据至少支持 Markdown/JSON 导出和 SQLite 备份，降低试用风险。 |
| P0 | UI 可用性打磨 | 优化确认、纠错、详情阅读和搜索结果排序。 |
| P1 | Todo 状态管理 | 支持 TODO 完成、取消、合并和来源追溯。 |
| P1 | Bucket 生命周期 | 支持 paused、done、archived 的明确操作和列表过滤。 |
| P1 | 数据迁移机制 | 为后续表结构变更建立轻量 migration。 |
| P2 | 语义检索 | 数据量增长后引入 embedding，提高“想不起来关键词”时的找回能力。 |
| P2 | 附件和更多输入 | 支持截图、文件、网页摘录或浏览器快捷入口。 |

## 8. 成功指标

### 8.1 MVP 验收指标

- 连续 7 天真实使用后，用户仍愿意把碎片信息输入系统。
- 高置信度自动归档准确率达到 90% 左右；整体分类准确率达到 70% 以上。
- 请求确认的比例可接受，且明显低于手动整理成本。
- 纠错动作能在 30 秒内完成。
- 用户能通过搜索找回至少 80% 的近期关键事务。
- 结构化摘要、证据、TODO、时间线和决策对复盘有实际帮助。

### 8.2 后续产品指标

- 每周活跃 bucket 数量。
- 每个 bucket 的平均 entry 数和有效结构化记录数。
- 自动归档后被纠错的比例。
- 搜索无结果或点开后无效的比例。
- 用户主动关闭、归档或完成 bucket 的比例。
- 导出或备份成功率。

## 9. 后续继续完成规划

### 阶段 A：真实可用性验收（1 周）

目标：确认当前 MVP 在真实模型和真实输入下是否足够可靠。

任务：

1. 配置可用的 OpenAI 官方或兼容中转站 API。
2. 执行真实分类评估：`python -m app.live_evaluation --limit 3 --output /tmp/classification-live-report.json`。
3. 执行真实提取评估：`python -m app.live_extraction_evaluation --limit 3 --reference-date 2026-08-03 --output /tmp/extraction-live-report.json`。
4. 人工审查报告中的错误类型：误追加、误新建、过度询问、事实遗漏、事实编造。
5. 根据报告调整 Prompt、候选策略和置信度阈值。
6. 补充不少于 20 条真实使用样例到 fixtures 或评估文档。

验收标准：

- 真实评估报告可复现保存，并记录模型、站点、Prompt 版本和日期。
- 至少完成一次分类阈值校准说明。
- 新增样例能通过 mock 回归，不依赖真实 API 跑普通测试。

### 阶段 B：数据安全与迁移基础（1 周）

目标：让用户敢把真实工作信息放进系统。

任务：

1. 增加一键 SQLite 备份能力，备份文件带时间戳。
2. 增加 Markdown/JSON 导出能力，按 bucket 导出原文和派生结构。
3. 明确本地数据路径、`.env`、数据库文件和导出文件的 git 忽略规则。
4. 设计轻量 migration 方案，避免模型变更破坏已有数据。
5. 在 README 和开发文档中补充备份、恢复、导出说明。

验收标准：

- 能在 UI 或命令行完成备份和导出。
- 新增自动化测试覆盖导出内容和备份文件生成。
- 文档说明哪些文件不可提交。

### 阶段 C：UI 体验闭环（1～2 周）

目标：把“技术 MVP”变成日常可用工具。

任务：

1. 优化首页信息架构：输入框、当前焦点、最近结果、待确认事项、活跃 bucket。
2. 改进 bucket 详情页：按摘要、时间线、TODO、证据、决策、原文分区展示。
3. 增加 TODO 完成/取消操作。
4. 增加 bucket 状态切换：active、paused、done、archived。
5. 增强纠错入口：移动到已有 bucket、创建新 bucket 后移动、修改 bucket 类型。
6. 增加空状态、错误提示和模型/API 配置提醒。

验收标准：

- 用户无需查看终端即可完成输入、确认、查看、搜索和纠错。
- UI 关键路径有测试或可重复手工验收脚本。
- 不确定分类不会被 UI 展示成成功归档。

### 阶段 D：长期记忆质量提升（2 周）

目标：降低长期使用后的噪音和混乱。

任务：

1. 根据纠错记录统计常见混淆 bucket 类型和主题。
2. 增加 bucket 合并建议，但默认不自动合并。
3. 建立滚动摘要的重建和版本策略。
4. 持久化或显式放弃 `hypotheses`、`entities`，避免半成品字段长期悬空。
5. 为决策替代关系和 TODO 合并设计数据结构。
6. 扩充提取评估集，加入人工 precision 和事实忠实性审查。

验收标准：

- 用户能看出每个长期 bucket 的当前状态、关键结论和下一步。
- 摘要错误可以通过重建或纠错恢复，不污染原文。
- 至少形成一份真实纠错分析报告。

### 阶段 E：检索与输入增强（2～4 周）

目标：提升找回能力和输入覆盖面。

任务：

1. 在有足够真实查询样本后评估语义检索收益。
2. 引入 embedding 存储与重建脚本，保留关键词搜索兜底。
3. 支持按时间、类型、状态、标签过滤 bucket。
4. 设计截图、文件或网页摘录的最小输入协议。
5. 明确附件原文、提取结果和引用来源之间的追溯关系。

验收标准：

- 用户忘记精确关键词时仍能找回相关 bucket。
- 语义检索结果必须展示命中的原文片段或来源。
- 附件能力不破坏现有文本归档路径。

### 阶段 F：个人长期可用版本 v1.0（持续）

目标：形成可以长期运行、可备份、可迁移、可解释的个人工作记忆产品。

任务：

1. 完成设置页：API 站点、模型、阈值、数据路径、导出路径。
2. 完成备份恢复和导出导入。
3. 建立版本化 Prompt 与评估报告管理。
4. 制定数据保留和本地隐私说明。
5. 梳理安装、升级和故障排查流程。
6. 根据真实使用反馈决定是否开发桌面入口、浏览器插件或移动快捷输入。

验收标准：

- 新用户可按 README 在本地完整启动并完成一次归档闭环。
- 升级不会丢失已有 bucket 和 entry。
- 真实模型、mock 测试和人工验收边界在文档中清晰区分。

## 10. 推荐下一步执行清单

如果继续开发，建议按以下顺序推进：

1. **先跑真实模型小样本评估**：确认当前分类和提取的真实质量。
2. **补导出/备份**：降低真实使用风险，是从 demo 走向个人工具的基础。
3. **补 TODO 状态和 bucket 状态管理**：让记录能变成可行动工作流。
4. **打磨 Streamlit 详情页和纠错体验**：减少用户因误归档放弃使用的概率。
5. **积累 7 天真实输入样本**：用真实数据决定是否上语义检索、附件和更复杂记忆结构。

## 11. 主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| LLM 自报置信度不可靠 | 高置信度误归档污染长期记忆 | 用真实评估和纠错数据校准阈值；候选不唯一时保守询问。 |
| 结构化提取幻觉 | 摘要或证据误导用户 | 原文永远保留；派生记录显示来源；增加事实忠实性评估。 |
| 长期 bucket 膨胀 | 详情页难读、搜索噪音增加 | 增加生命周期、合并建议、摘要重建和归档机制。 |
| 本地数据丢失 | 用户不敢长期使用 | 优先实现备份、导出、恢复和迁移。 |
| UI 过于工程化 | 用户输入和纠错成本高 | 以单入口、清晰确认、低成本纠错为设计核心。 |
| API 配置复杂 | 新用户启动失败 | 设置页、错误提示和配置文档同步完善。 |
