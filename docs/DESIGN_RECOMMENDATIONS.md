# 设计推荐：结合竞品后的产品与技术建议

## 1. 产品形态建议

### 推荐形态

```text
一个输入流 + 多个自动维护的 bucket + 若干结构化视图
```

用户只看见简单输入框，但系统内部维护复杂结构。

## 2. 信息架构建议

### 2.1 不要把 bucket 做成文件夹

文件夹的问题是：

- 强制单归属。
- 容易变成静态堆放。
- 用户需要提前想分类。

bucket 应该是：

- 有标题。
- 有类型。
- 有状态。
- 有摘要。
- 有时间线。
- 有证据。
- 有待办。
- 可与其他 bucket 关联。

### 2.2 Entry 永远保留原文

LLM 提取可能出错，所以必须保存 raw_text。

推荐：

```text
原文是事实层。
结构化字段是解释层。
总结是压缩层。
```

不要用总结替代原文。

### 2.3 类型模板要“系统内置”，不要一开始让用户配置

受到 Capacities/Tana 启发，结构化对象很有价值。但新手产品不要让用户设计 schema。

第一版内置模板：

- incident：现象、影响、证据、时间线、假设、验证、处置、复盘。
- experiment：目标、参数、结果、对比、结论、下一步。
- meeting：参会人、议题、结论、待办、争议。
- idea：问题、想法、目标用户、价值、风险、下一步。
- decision：决策、背景、备选方案、原因、影响。

## 3. 交互建议

### 3.1 每次归档都要给用户反馈

不要默默保存。反馈模板：

```text
已归档到「{bucket_title}」
类型：{bucket_type}
动作：{append/create}
置信度：{confidence}
原因：{reason}

如果不对，你可以说：把刚才那条移到 XXX。
```

这样用户会建立信任。

### 3.2 高置信度自动做，其他情况先确认

长期记忆一旦误合并，清理成本高于多确认一次。MVP 采用保守策略：

- >= 0.85 且候选唯一：直接归档；
- 0.55 - 0.85：确认后归档；
- < 0.55：必须确认；
- 多个相似候选：即使分数较高也确认。

这些阈值是待评估数据校准的初值，不能把 LLM 自报 confidence 当成真实正确概率。

### 3.3 纠错语言要宽容

用户可能这样说：

- 不是这个。
- 刚才那条放错了。
- 移到支付问题。
- 单独记。
- 这应该算实验，不是任务。

系统要能映射到有限操作：

- move_entry
- create_bucket_from_entry
- change_bucket_type
- merge_buckets
- link_buckets

### 3.4 输出视图不要只有聊天

借鉴 Notion AI 的文档化输出思路：

- incident 输出复盘模板。
- experiment 输出对比表。
- meeting 输出会议纪要。
- idea 输出 idea card。
- task 输出 TODO 列表。

MVP 可以先用 Markdown 渲染。

## 4. 技术实现建议

### 4.1 第一版先做单体，不做多 Agent

原因：

- 新手更容易理解。
- 业务流程还在探索。
- 多 Agent 会增加调试难度。

第一版模块拆分：

```text
archive_service
classify_service
extract_service
bucket_service
correction_service
search_service
view_service
```

### 4.2 用 Structured Outputs 保证 JSON 稳定

分类和提取都需要稳定 JSON。建议使用 Pydantic schema + OpenAI Structured Outputs。

### 4.3 搜索先用 SQLite，后续再上向量

MVP 阶段：

```sql
WHERE title LIKE ? OR summary LIKE ? OR raw_text LIKE ?
```

当数据变多后升级：

- 关键词检索。
- embedding 语义检索。
- recency 加权。
- bucket 类型过滤。

### 4.4 摘要采用 rolling summary

不要每次把完整历史传给模型。

每次归档后：

```text
旧 bucket summary + 新 entry summary → 新 bucket summary
```

这样成本更低，也更接近长期记忆系统。

### 4.5 纠错要写入 corrections 表

每次用户纠错都很宝贵。

例如：

```text
用户多次把“压测、P99、QPS”从 task 改到 experiment
```

系统以后就应该提高 experiment 判断权重。

## 5. 视觉与页面建议

### MVP 页面

```text
┌──────────────────────┬────────────────────────────┐
│ 活跃 Buckets          │ 输入框                       │
│ - 支付回调失败排查     │ [把碎片信息丢进来...]          │
│ - 接口 A 压测          │ [归档]                       │
│ - 首页改版会议         │                              │
├──────────────────────┼────────────────────────────┤
│ Bucket 详情           │ 最近归档结果                  │
│ 摘要/时间线/TODO/证据  │ 已归档到...                   │
└──────────────────────┴────────────────────────────┘
```

### Bucket 详情视图

- 顶部：标题、类型、状态、更新时间。
- 第一屏：摘要和下一步。
- 第二屏：时间线和证据。
- 第三屏：原始记录。

## 6. 排障场景专项建议

你的文档里提到 incident，这是非常适合作为第一个强场景的类型。

incident 模板：

```text
# {title}

## 现象

## 影响范围

## 时间线

## 证据

## 假设

## 验证

## 处置

## 当前状态

## 待办

## 复盘
```

为什么适合 MVP：

- 信息天然碎片化。
- 用户很讨厌事后补复盘。
- 时间线、证据、结论价值明显。
- 容易验证是否省时间。

## 7. 实验场景专项建议

experiment 模板：

```text
# {title}

## 目标

## 参数

## 结果

## 对比

## 结论

## 下一步
```

适合记录：

- 压测结果。
- A/B 测试。
- 模型参数实验。
- 产品方案验证。

## 8. 风险与应对

| 风险 | 应对 |
|---|---|
| 自动分类不准 | 置信度 + 可纠错 + correction log |
| 用户不知道系统做了什么 | 每次归档给解释 |
| bucket 越来越乱 | 支持合并、归档、推荐整理 |
| 摘要丢失细节 | 永远保留 raw_text |
| LLM 成本高 | rolling summary + 只传活跃 buckets |
| 用户不持续输入 | 输入体验必须比记笔记更轻 |

## 9. 最重要的设计取舍

第一版宁可：

- UI 简陋一点。
- 类型少一点。
- 搜索简单一点。
- 只支持文本。

也要确保：

- 自动归档闭环顺畅。
- 结构化结果有用。
- 纠错真的方便。
- 历史能找回来。
