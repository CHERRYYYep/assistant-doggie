## 4. 失败归因与真实运行期发现

| 编号 | 级别 | 归因层 | 复现样本与实际表现 | 修复方向 |
|---|---|---|---|---|
| **C4-1 (S16)** | **P1** | 意图/材料判定 (`chat-purpose.ts`) | 库中存在唯一完整标题 Entry「TCP 抓包与三次握手」，用户输入 `把「TCP 抓包与三次握手」改成一句正式报告表述，不新增事实` 被误判为自带原文改写，仅改写了 9 字标题本身，丢掉了 `18ms` 等 Entry 事实。 | 引号文本先与本地有效 Entry/WorkItem 标题做精确/唯一核对（或区分短标题与长正文），命中唯一有效记录时优先走记录定位而非裸字改写。 |
| **C4-2 (S32)** | **P2** | 意图判定 (`chat-purpose.ts`) | 存在两个同名 WorkItem「计网实验报告」，用户输入 C0 样本原话 `接着改计网实验报告` 掉入泛问，未触发同名澄清。 | 补充「接着改 / 继续改 / 续写…」等续做前缀进入目标定位分支。 |
| **C4-3 (S12)** | **P2** | 材料边界 (`chat-purpose.ts`) | `原文：……请仅将第一句改写为正式说明。` 因指令含「仅将第一句」修饰词未被识别为尾部改写指令，退回为裸原文问目的（无安全泄露，但多问一轮）。 | 放宽 `原文：` 后尾部改写指令的句式匹配，同时保持材料内部指令隔离。 |
| **C4-4 (P5 显式)** | **P2** | 主对话服务 (`main-conversation.ts`) | 显式携带 `replyTo` 指向零候选澄清卡并粘贴 `原文：...` 时，未能像自然输入那样接回原请求并绑定本轮材料消息。 | 统一零候选卡在自然续接与显式 `replyTo` 下的本轮材料消息绑定路径。 |
| **C4-5 (S20/S24)** | **P2** | 意图路由 & Harness Prompt | 不含「上次/我」的个人事实提问（如「发布审批的联系人邮箱是什么？」）走了 `answer` 而非 `lookup`；且 S24 中模型把内部 JSON 字段名 `` `archive` 字段也为空 `` 暴露进了用户可见回复。 | 1）`answer` 路径不再向用户消息 JSON 传 `archive: null`，或在提示词禁止提及内部字段名；2）评估个人实体/记录问句进入只读 `lookup` 的规则覆盖。 |
| **C4-6 (S13 超时)** | **观察** | 上游模型延迟 / 超时配置 | `gpt-6.1-sol` 在 S13 首次调用耗满 30s 触发超时（30,027ms），重跑 8.05s 成功；P1 单轮也曾达 14.5s / 26.1s。 | 文档说明推理型模型建议调高 `OPENAI_TIMEOUT_SECONDS`（如 60s），不改变既有超时失败/重试合同。 |

## 5. 默认入口决策建议

1. **当前决定**：**保持自然对话预览默认关闭**，暂不将主输入默认切换为新路径。
2. **理由**：
   - 在真实模型下，自然对话在三路径对照（5/5 vs 旧入口 0/5 干净达成）、数字保真（0 编造 / 实际改写 0 遗漏）、无证据拒答（6/6）、撤销防回流（2/2）和冲突拦截方面已显著优于旧聊天；
   - 但 **C4-1 (S16)** 属于用户明确用引号引用完整记录标题却丢失正文事实的 P1 级体验问题，**C4-2 / C4-3 / C4-4 / C4-5** 也有清晰确定的根因与极小修复面。
3. **放行条件**：完成 C4-1 至 C4-5 的小批次代码修复与单测回归，并对受影响的 6–8 个场景执行一轮低成本定向真实模型复验（≤ 15 次请求）确认清零后，即可做出默认入口切换决策。
