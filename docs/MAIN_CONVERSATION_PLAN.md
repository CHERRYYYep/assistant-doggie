## 1. 希望交付的体验

用户隔天打开同一入口，说「帮我改那个计网实验」。Doggie 若知道有 TCP 抓包和 UDP 丢包两个实验，就列出二者，问一句能区分它们的问题。用户说「抓三次握手那个，只改报告，SYN 和 SYN-ACK 写反了」后，助手接回最初的修改请求：有原文就给出改写，没有就请用户提供段落，或提议只读检查指定工作区。第一版不会代写磁盘文件。若用户一开始就给了完整段落和改写要求，直接回答；问「SYN-ACK 是什么」也不必先选实验。

产品目标是减少**重复交代、选错目标和无谓追问**。主对话保存互动经过；WorkItem 保存目标和验收要求；执行尝试关联 AgentSession，仅在同目标、同工作区、范围和记忆版本等条件仍有效时恢复；Bucket 继续按主题组织 Entry 和派生 Memory。一个 Bucket 可以帮助找到多个目标，一个目标也可引用多个 Bucket/Entry。选择 Bucket 不代表选择目标、恢复会话或批准执行。T14 TODO 是用户可独立编辑的待办，不能由一次执行成功自动完成。

## 3. 一轮对话怎样决定下一步

| 输入依据（优先检查显式关联） | 行为与副作用 |
|---|---|
| 用户点击既有归档确认、执行批准或拒绝 | 进入原专用接口。普通文本「好」「就这个」不是归档确认或执行批准。 |
| 明确回复某张澄清卡，或在该卡的回复框补充 | 核对原消息、澄清版本与服务端候选。若仍不清楚，只问剩下的一点；接受选择后显示目标名称。该回复不作为独立归档输入。 |
| 明确指定目标，或提出有依据的续做请求 | 按 ID/唯一完整标题解析；模糊简称只生成候选。候选只有一个但证据弱时可建议，不静默绑定。显示少量可区分候选及「都不是／补充描述」。完成的历史目标可作为资料或明确重开的对象，不自动重开。只有 Entry 而没有 WorkItem 时可据其回答或提议创建目标，不伪造既有任务。 |
| 普通知识问答、用户给定段落改写、查询既有记录 | 不强制创建目标。通用问题直接回答；涉及「我上次……」的个人事实须有有效来源，资料不足就指出具体缺口。 |
| 新工作记录、明确「记一下」、或无法区分用途的低信息输入 | 工作记录继续走原归档规则；不确定时沿用 `ask_user` 或澄清用途，不静默写入。已在等待的归档提案仍保留。多目标输入只请用户先选一个，不静默拆成并行任务。 |

允许插话。若澄清卡仍在等待，用户另问一个完整问题，应先答新问题，卡片保持可恢复。主输入框可以显示可取消的「回复：TCP 还是 UDP」提示；只有明确的回复关联才提交到该卡，多张卡并存不按全局最后一条猜测。模型可以从服务端提供的候选中建议意图或组织问句；服务端决定合法目标和副作用。模型不可用时，候选按钮、确定性解析、老的归档与目标入口仍可用。

## 4. 上下文、记忆和执行分别读取什么

- **回答当前句子**：固定系统规则、原请求和已绑定的补充优先保留；近期对话只作语言背景。已有目标时，按 ID 取目标、验收要求、状态、最近一次尝试及当前有效的关联来源。任务上下文显式组装，不能把已过滤的任务消息全部灌回普通历史。
- **查找材料**：关联材料足够就停止；不足时用本地 `search_memory` 找少量候选，再检查来源是否有效、内容能否回答所问。Bucket 标题、索引分数和模型摘要不能单独证明事实。例：「发布审批」记录没有手机号，答案就是「这条记录没有号码」。引用可打开的 Entry；涉及目标状态时引用 WorkItem。第一版在现有字节预算内先裁重复候选和旧闲聊；必要内容放不下则缩小问题，不截掉约束后继续执行。
- **执行交接**：把用户明确的要求、目标 ID/范围版本、工作区、只读能力及有效资料引用交给现有提案流程。批准与启动时复核；取消、范围或来源失效时拒绝复用旧批准/会话和迟到结果。一次目标同时最多一个有效执行尝试。主对话展示任务 ID 对应的结果；结果进入时间线不等于成为长期事实，保存走既有归档规则。

## 5. 增量重构顺序与交付件

每阶段独立提交；路径中只有链接指向已有文件，新增类型和接口名均为提议。R0–R5 完成后，C0 复用已固定的旧行为回归，新增产品场景；C1 复用已抽出的 ChatService，仅加入意图分流，不重新搬运 HTTP 编排。

| 阶段 | 具体改动 | 完成条件 |

| C3 本地取证与受控委派 | 抽出上下文组装函数；接入现有 WorkItem 来源、查询服务、Harness 与提案服务。前端复用现有卡片/任务状态，主时间线关联提案和结果。 | 已给材料直接答；缺材料能说明缺口；需要工作区时先提案、批准后才执行；重开、取消、撤销及晚结果有回归。 |
| C4 对照与默认切换 | 在完全相同的 fixtures 上比较旧聊天、主对话＋本地检索；记录每一步错在意图、候选、绑定、证据还是执行。满足 §6 后再把新主输入设为默认。 | 提交结果、适用范围和失败样例，运行 `npm run check`；达不到要求保留旧入口，优先修出现频率最高的具体失败。 |

**建议的 API 和数据演进。** 保持现有 `POST /api/chat`、`/api/chat/confirm` 和 `/api/work-items/...` 不变，给新界面增设 `POST /api/conversation/turns`，用判别字段区分新发言、回复某条澄清、选择候选或取消。响应区分回答、澄清、原归档结果或执行提案，均有可重读的消息引用；该接口不接受批准字段。请求含 `requestId`；回复含 `clarificationId` 和 `expectedRevision`。按 [API 契约规范](API_CONTRACT.md) 从 schemas 生成 DTO/OpenAPI，添加历史恢复投影、浏览器校验、资源上限与漂移测试；不悄悄改旧客户端返回形状。

C2 建议在实施时使用 v8 的下一次正式迁移，为澄清保存原消息 ID、候选 ID/范围版本、缺少的描述、状态 `pending/resolved/cancelled/stale`、选定目标及 revision；明确 reply-to 关联和请求幂等记录。只存引用，展示/消费时重新检查目标与来源；失效就提示重选。用同一事务绑定选择、写回复与更新状态；双击同请求返回同一结果，同键不同载荷或另一页陈旧选择返回冲突。模型与 CLI 调用都在事务外。仅用临时旧库验证迁移、重开和回滚。发布开关关闭后回旧界面与旧请求路径，已发起提案仍可查；不承诺旧程序可读新 schema。真实库升级前另做一致性备份和恢复演练。

## 6. 验收：既不能猜错，也不能什么都问

| 冻结的合成情境 | 要观察的结果 |
|---|---|
| 两个计网实验，同一 Bucket；同名不同目标；只匹配到一个弱候选 | 问能区分的问题且允许「都不是」；无错误绑定、自动保存、启动或批准。 |
| 「抓三次握手那个，只改报告」；明确全名；已给出要改的段落；单纯问术语 | 有关联时接回原请求；信息齐全不再追问；通用问答不创建任务。 |
| 等待澄清时插话；两个页面选不同目标；重复请求；刷新或重启 | 各回复绑定正确原文；陈旧选择冲突；同请求只消费一次。 |
| 没有目标但有历史材料；已完成的目标；已撤销来源；命中主题却缺答案 | 可提议新目标或读材料；不自动重开；无效证据不进入回答；没有证据时明确说明。 |
| 新工作记录、独立的模糊归档、确认/不保存和纠错，与任务卡交错 | 原归档四选项、双审计事务和防重放不退化；澄清不是批准。 |
| 确认了目标后要检查文件；变更工作区；执行中取消或撤销资料 | 原只读批准链、单目标排他和失效检查仍生效；结果不串目标、不写文件、不自动完成目标。 |

分别统计：需澄清样本中直接错绑数、信息齐全样本中多余追问数、目标绑定正确率、证据遗漏与无证据误答、重新描述次数。按各类样本分母分别报告；C2–C4 的固定合同样本要求预期分支全部通过，错绑执行、越权、撤销材料回流为零。记录证据 ID、分支和结果，不收集真实对话或原始模型日志。普通门禁仅 fake model/runner 和临时 SQLite；它能证明流程与约束，不能证明真实模型理解任意自然语言。后续更大样本、真实体验与显式预算的模型评测单列。

## 7. 什么时候才值得换检索方案

先给每次失败归因：对象选错，改澄清；已绑定目标但关联材料没读到，改按 ID 读取；证据在资料库却因措辞不同没召回，才比较词法、向量或混合检索；只在过去未归档的聊天提过，则是**历史聊天可检索范围**的产品决定，向量引擎本身不能替用户同意保存。撤销或证据不足的问题先修有效性检查与弃答。

[现有 D3 固定样本](D3_L0_RECOVERY_PLAN.md)中，Core 与本地的正查询 Recall@5 分别为 83.33% 和 58.33%，无证据查询正确返回空为 6/12 和 9/12；这不是对话体验或向量能力的比较。把 D3 留作对照，暂不把腾讯候选送入正式回答。只有本地纵向链路过验收、独立样本显示跨目标召回有损失，再按[腾讯接入总设计](TASK_MEMORY_INTEGRATION_DESIGN.md)评估受测版本；回答质量、弃答及撤销同时过关才考虑 D4b。腾讯故障不应妨碍本地聊天、归档、审批或执行。
