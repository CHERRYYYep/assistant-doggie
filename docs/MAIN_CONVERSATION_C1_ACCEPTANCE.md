# C1 主对话用途分流验收

2026-11-19 · 实施分支 `codex/main-conversation-backend` · 接续 C0 提交 `7c32280`。

C1 在 [ChatService](../src/application/chat.ts) 提供内部 `mainChat` 入口。新旧聊天和归档确认共用同一个轮次协调器、历史上界和回复事务；线上 `/api/chat`、后台聊天队列、确认接口和网页行为均未切换。没有数据库迁移、公开接口变更或额外的模型分类调用。

| 用途 | 示例 | 本阶段行为 |
|---|---|---|
| 直接回答 | 「SYN-ACK 是什么？」、提供原文的改写 | 只调用回答模型，不查记忆工具、不创建 Entry 或 WorkItem。 |
| 只读取证 | 「上次发布审批是什么时候？」 | 调用现有回答 Harness，保留限定的只读记忆工具；提示模型用有效 Entry 支撑个人事实，缺证据就说明。 |
| 归档 | 「记一下：接口 p99 从 62ms 降到 31ms」 | 复用原分类、低信息门控、确认与归档事务。 |
| 澄清 | 「帮我修改那个计网实验」「好」或混合多个请求 | 针对缺少的目标或用途反馈；「好」提示使用对应的确认入口。不自动选择目标或消费审批。 |
| 标记执行诉求 | 「只读检查 TCP 抓包报告」 | 识别需要执行交接；C1 只提示下一步，不创建提案、启动任务或修改文件。 |

[用途规则](../src/domain/chat-purpose.ts)是保守的确定性分流：识别明确问题、引用材料、个人记录查询、显式保存和少量无歧义的指标陈述。未匹配的输入先澄清。它没有覆盖所有自然表达；直接回答与取证的模型质量、本地材料的命中率和无证据弃答率也未在 C1 评估。C1 的取证使用既有 Harness，按已选目标组装证据和受批准的执行提案由 C3 实现。

[应用层回归](../src/application/main-chat.test.ts)使用 C0 的明确问题和改写样本，验证这些分支不运行归档分类，并检查归档确认独立、无隐式任务写入和取消/撤销时丢弃迟到结果。两种 API mode 另有 [Harness 回归](../src/agent/harness.test.ts)，验证直答不公开工具、取证不能执行写工具。C0 的 HTTP 基线继续通过。

64 项定向回归全部通过；`npm run check` 通过（561 项后端、60 项前端，零失败、取消、跳过），`git diff --check` 通过。使用替身和临时库，未调用真实模型或读取真实库。

下一阶段 **C2**：接出新的主对话 API 和最小交互，持久化原请求、候选和选择；依次验证「那个计网实验 → TCP／UDP 候选 → 明确回复 → 刷新后继续」，以及重复请求和陈旧选择。暂不切换旧入口的默认行为。
