# PRD：个人工作整理 Agent

> 2026-11-03 范围确认：当前继续个人本地助手，先完成现有功能链路与 T13 收口。多人协作仅保留远期想法；手机接入电脑端只做接口文档预留。决定与实施状态见 [PRODUCT_DECISIONS.md](PRODUCT_DECISIONS.md)。

## 1. 产品一句话

个人工作整理 Agent 是一个“单入口、多上下文”的工作记忆系统：用户把碎片信息丢进一个输入框，系统自动判断归属、沉淀结构化内容，并持续维护多个可追踪的工作 bucket。

## 2. 目标用户

第一阶段聚焦个人用户，而不是团队协作：

- 开发者：排障、实验、代码方案、技术决策。
- 产品经理：需求想法、用户反馈、会议结论、待办。
- 创业者/独立开发者：灵感、调研、项目推进、复盘。
- 研究/学习者：实验记录、读书笔记、长期知识。

## 3. 核心痛点

用户每天产生大量碎片信息，但传统工具要求用户主动：

- 创建文件夹或页面。
- 判断归类。
- 维护标题、标签、链接。
- 手动总结和追踪待办。
- 事后搜索和恢复上下文。

结果是：很多信息被丢在聊天记录、截图、临时文档和脑子里，无法复用。

## 4. 产品目标

MVP 目标不是替代 Notion、Obsidian 或任务管理工具，而是验证一个核心假设：

> 如果输入足够简单、整理足够自动，用户是否愿意持续把碎片工作信息丢进来。

## 5. 核心对象：Bucket

Bucket 不是普通文件夹，而是一个“活的上下文对象”。它包含：

- 状态
- 摘要
- 时间线
- 原始输入
- 证据
- TODO
- 决策
- 关联对象

第一版 bucket 类型：

| 类型 | 用途 |
|---|---|
| idea | 产品想法、设计灵感 |
| task | 具体待办事项 |
| incident | 线上问题、排障记录 |
| experiment | 测试结果、实验记录 |
| decision | 已形成判断及原因 |
| meeting | 会议纪要、讨论结论 |
| knowledge | 长期稳定知识 |
| draft | 文档、方案、文章草稿 |

## 6. MVP 用户故事

### 用户故事 1：自动归档

作为用户，我输入一条碎片信息，希望系统自动判断它应该归档到哪里，并告诉我结果。

验收：系统返回 bucket 标题、类型、置信度和原因。

### 用户故事 2：自动新建 bucket

作为用户，我输入一个新主题，希望系统自动创建新的 bucket。

验收：当没有合适 bucket 时，系统创建新 bucket 并保存内容。

### 用户故事 3：继续已有上下文

作为用户，我输入“刚才那个问题恢复了”，希望系统理解这是在继续已有 bucket。

验收：系统在服务端自动生成的最近/热门候选中找到相关 bucket，并在信息充分时追加；信息不足时先询问确认。

### 用户故事 4：结构化沉淀

作为用户，我希望系统自动从输入中提取摘要、证据、时间线和 TODO。

验收：bucket 详情页可以看到这些结构化内容。

### 用户故事 5：自然语言纠错

作为用户，如果系统归错了，我希望直接说“刚才那条放到另一个 bucket”。

验收：系统能移动最近 entry 或修改 bucket 类型。

### 用户故事 6：历史恢复

作为用户，我希望过几天还能找回之前的问题或实验。

验收：用户搜索关键词，系统返回相关 bucket。

## 7. 非目标，第一版暂不做

- 多用户登录和权限系统。
- 移动端 App。
- 团队协作。
- 大规模文件知识库。
- 自动执行外部操作。
- 复杂图谱可视化。
- 多 Agent 协作框架。
- 生产级加密和审计。

## 8. 成功指标

MVP 阶段用定性和轻量量化指标：

- 用户是否愿意连续 7 天输入碎片信息。
- 自动分类准确率是否能达到 70% 以上。
- 用户纠错成本是否低于手动整理成本。
- 用户是否会主动回来查询历史 bucket。
- bucket 摘要、时间线、TODO 是否真实有用。

## 9. 产品原则

- 单入口优先：不要让用户先选择分类。
- 默认自动：系统处理 90%，用户校正 10%。
- 可解释：每次归档都说明原因。
- 可撤销：自动化必须允许用户纠错。
- 原文保留：结构化提取不能擅自覆盖或丢失原始输入。用户显式撤销是独立操作；撤销后其专属派生记忆退出有效记忆，彻底清除另行定义。撤销已实现，见 [撤销合同](ENTRY_REVOCATION.md)。
- 渐进增强：先本地文本 MVP，再做文件、截图、知识库。

## 10. 后续接入与架构边界

统一输入入口不要求使用无限、无差别的模型上下文。前端先完成功能 MVP，再开展可能较大的视觉改版。

个人多设备的设想是手机配对连接电脑上的 Doggie，数据与执行环境以电脑为中心，不是离线多库同步。当前仅记录未来操作边界，不提供远程访问或公网部署能力，见 [REMOTE_ACCESS.md](REMOTE_ACCESS.md)。

API 契约/OpenAPI、框架演进与部署方式纳入近期设计评估，但尚未决定迁移框架或实施分布式系统。T14–T17 在现有质量收口后重新排序。
